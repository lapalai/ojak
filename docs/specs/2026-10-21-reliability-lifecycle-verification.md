# Ojak 전 생명주기 안정성 검증 계획 — 최종본

- 작성일: 2026-10-21
- 상태: 검증 계획 최종본. 문서 확정은 구현·테스트 실행·설치·삭제·업데이트·배포의 승인 또는 완료가 아니다.
- 대상: Ojak 앱/CLI/서비스, omp 호환 수정본, 공식 Claude Code, 공식 Codex.
- 플랫폼: macOS Apple Silicon 및 native Windows x64. Windows를 Mac의 mock 결과로 대체하지 않는다.
- 목표: 정상 사용뿐 아니라 설치 → 연결 → 실행 → 장애 → 복구 → 업데이트 → 삭제 → 재설치의 사용자 결과를 입증한다. 부하 성능 수치는 별도이며 이번 계획의 중심은 정확성·안전성이다.

## 문서 요약

**기존 사용자의 작업 환경을 망가뜨리지 않고 Ojak을 도입·사용·업데이트·제거할 수 있는지**를 확인한다. 사용자 여정 12개와 이를 뒷받침하는 기술 시나리오 87개를 연결한다. 사용자 여정은 기술 시나리오를 묶는 상위 흐름이므로 두 수를 더해 테스트 건수로 보고하지 않는다. OS·설치 채널·장애 시점별 실제 실행 건수는 더 많다.

- **현재 판정:** 이 최종본의 시나리오 실행은 `NOT_RUN`. 기존 테스트의 존재·과거 일부 검증·정적 코드 검토와 이번 계획의 통과 여부는 별개다.
- **확인된 환경:** 운영 Windows PC의 SSH 접속과 x64 아키텍처만 확인했다. 전용 파괴 테스트 환경은 아직 확보하지 않았다.
- **최초 도입 게이트:** 기존 사용자 설치 → 작업 중 설치 → 설치 전 대화 재개 → 삭제 후 원본 복귀를 먼저 검증한다.
- **핵심 안전 게이트:** 불명 요청 재전송, 잘못된 계정 실행, 사용자 데이터 훼손, 사용 중 설치/제거/업데이트에 따른 작업 손실이 없어야 한다.
- **범위 밖:** 부하 처리량 최적화, 공급자 한도·결제 정책 변경, 인증 우회, 전체 데이터 purge 기능 신설, 사용자 승인 없는 운영 배포.

## 1. 핵심 결정과 검증 한계

1. **전체 E2E는 전용 VM 또는 전용 테스트 호스트에서 실행한다.** 현재 public bridge는 `4020`, broker는 `8765`, gateway는 `4101–4199`를 사용한다. `AAM_HOME`/`HOME`만 바꾼 두 번째 서비스를 운영 Mac에서 띄우는 것으로 격리를 보장할 수 없다. 다른 OS 사용자도 TCP 포트를 공유한다.
2. 로컬의 빠른 검증은 기존 Rust의 OS 할당 포트 harness와 임시 DB·합성 credential fixture를 재사용한다. 실제 omp 실행 파일을 포함하는 전체 경로, LaunchAgent/Windows 자동 시작, Keychain/OS credential store, NSIS/DMG 검증은 전용 OS 환경으로 올린다. 포트 override라는 제품 기능 추가를 선행 조건으로 삼지 않는다.
3. 테스트 VM에는 운영 홈·Keychain·인증 파일을 복사하거나 호스트 홈을 공유 마운트하지 않는다. 테스트 전용 OS 사용자와 공식 로그인으로 승인된 테스트 계정을 준비한다. 인증된 VM snapshot/덤프는 비밀 자료이며 CI artifact로 올리지 않는다.
4. 라이브러리 대역, 실제 바이너리+가짜 공급자, 실제 계정 호출, 실제 서명 설치 파일의 결과를 서로 대체하지 않는다. `ai.streamSimple` 대역을 사용하는 시뮬레이션만으로 실제 클라이언트 경로를 입증할 수 없다. 실제 pi-native의 예외/이벤트 경로 검증은 별도 필수다.
5. `BRIDGE_EXECUTION_UNKNOWN`의 코드만 맞추지 않는다. 사용자가 본 `전달한 요청의 완료 여부…`는 `aam-accounts.js` catch 경로이고, `응답 완료를 확인하지 못해…`는 error 이벤트 경로다. 실제 pinned pi-ai를 통해 각각 발생 조건을 확인한다. 문구 자체를 고정하는 회귀 테스트 대신 분류·원인 보존·POST 수·journal 상태를 판정한다.
6. 외부 공급자까지 exactly-once를 보장한다고 주장하지 않는다. 우리 경계에서 **전송 가능성이 있는 요청의 자동 재전송 방지**를 검증한다. 명시적 미전송 대기 응답은 복수 POST가 가능하지만 실제 공급자 실행은 중복되지 않아야 한다.
7. 전송 전에 보수적으로 `submitted`를 기록하는 fence 자체는 유지한다. `submitted` 기록 후 fetch 전 종료는 실제 미전송이어도 복구 때 unknown일 수 있다. 단순히 fetch 뒤로 기록을 옮겨 중복 실행 창을 만들지 않는다. 미전송 판정은 실제 transport가 제공한 확정 증거를 필요로 한다.
8. 테스트 과정에서 제품 결함이 발견되면 재현 근거와 계약을 확정한 뒤 수정한다. 이 문서는 무조건 재시도, 인증 우회, lease 강제 해제, 자동 과금 활성화 권한을 주지 않는다.
9. **정적 검토에서 발견한 보호 공백:** `crates/service/src/lib.rs::prepare_uninstall`은 native 점유 lease만 검사하며 활성 omp 스트림/대기/인증 갱신은 검사하지 않는다. `deactivate.rs`는 서비스 미접속 시 permit 없이 연결 해제를 진행한다. 이 두 경로를 R04/R12/U03의 최우선 재현 대상으로 둔다. 종단 실패는 아직 실행하지 않았으며, 기존 게이트가 모든 작업을 보호한다고 주장하지 않는다. bridge 활동은 `bridge.status.connections`·`modelQueue`·`authRefresh`로 관측하되, 단순 사전 조회와 종료 사이 경합도 주입한다. 실제 보호는 새 작업 admission 차단과 활동 확인의 원자적 경계가 필요하다.

| D: 배포 산출물 검증 | 이전 설치본 + 동일 서명 후보 DMG/NSIS/omp asset | 실제 설치·업그레이드·삭제·재설치·공개 업데이트 경로 |

공식 CLI에 가짜 공급자를 연결하려고 API key/base URL/auth helper 차단을 해제하지 않는다. 그 경로가 지원되지 않으면 장애 주입은 A의 모의 native CLI 또는 B의 서비스/프로세스/파일 시스템 경계에서 수행하고, 공식 CLI 모델 왕복은 C로 검증한다.

준비할 환경:
- [CONTRIBUTING.md](../../CONTRIBUTING.md)의 지원 범위를 기준으로 macOS arm64 현재 지원 OS와 최소 지원 OS(13+), Windows 11 x64와 최소 지원 Windows 10 1809+를 검증한다. Windows x64는 x64 하드웨어 기반 전용 물리/클라우드 호스트 또는 그 위의 VM을 사용한다. Apple Silicon의 Windows ARM/x64 에뮬레이션은 native x64 증거를 대신하지 않는다. 접근 불가 OS는 `BLOCKED`로 남기며 지원 전체 검증을 주장하지 않는다.
- 인증 없는 설치용 clean snapshot, 공식 CLI만 있는 snapshot, Ojak 이전 버전 snapshot, 현재 후보 snapshot. 인증 자료는 snapshot 외부 보관 또는 접근 제한·폐기 정책을 적용한다.
- 실행 전에 버전·SHA-256·설치 채널·OS build·정책·테스트 계정 별칭·포트 소유 PID를 기록한다. 설치된 파일 버전과 실행 중 서비스/CLI 버전을 따로 수집한다.
- 전용 VM 안에서도 포트 점유나 기존 설치 소유권이 예상과 다르면 중단한다. 임의 프로세스를 죽여 포트를 확보하지 않는다.
- 실제 공급자 호출은 범위·횟수·예산을 승인받은 뒤만 실행한다. 한도 소진을 만들기 위한 반복 호출·크레딧 결제·초기화권 사용은 하지 않는다. 실제 소진을 관측하지 못하면 fixture-only로 남긴다.

Windows GUI와 일반 사용자 설치 검증은 해당 사용자의 대화형 데스크톱에서 수행한다. SSH에서 명령이 성공한 것만으로 GUI/권한 검증을 대체하지 않는다. 보안 경고가 재현되지 않으면 보호 활성 상태와 경고 미발생을 기록하고, 경고·취소 경로는 별도 미실행/차단으로 남긴다. 백신을 일부러 감염시키거나 보호를 끄지 않는다.

## 4. 전 시나리오 공통 합격 기준

- 잘못된 identity/프로필/프로젝트 계정에서 실행하지 않는다. 인증 충돌은 차단하고 자동으로 설정을 고치지 않는다.
- 불확실한 spawn/모델 요청을 다시 시작하지 않는다. 서비스 응답 유실만으로 lease 슬롯을 반환하지 않는다.
- 완료 결과·도구 실행 결과·사용자 입력을 재실행용으로 삭제하지 않는다. 완료 후 저장 실패를 네트워크 미완료와 구분할 수 있어야 한다.
- 사용자 취소·종료한 세션과 닫힌 소유자를 자동 부활시키지 않는다. 정상 신규 작업의 복구 가능성과 안전 중단을 각각 검증한다.
- Ojak이 소유하지 않은 설정·실행 파일·로그인·프로세스는 보존한다. 사용자가 수정한 소유 파일도 충돌로 처리하고 덮어쓰지 않는다.
- 제품 로그/오류/진단/CI artifact에 token·이메일·프롬프트·인증 원문을 남기지 않는다. raw cause를 그대로 로그에 출력하지 않고 안전한 오류 종류·단계만 증거화한다.
- 종료 코드 0, ready 표시, 단일 정상 응답만으로 종단 성공 판정하지 않는다. 요청 수, 프로세스 수명, lease/journal, 실제 파일 결과를 함께 확인한다.
- 계획된 정상 종료·확정 취소 후 자원은 각 계약의 마감 안에 기준선으로 돌아온다. 미확인 lease의 보존은 누수와 구분한다.

Claude/Codex 각각 실제 다중 턴·임시 파일 작업·종료·재개를 C 등급으로 실행한다. 모델의 정확한 답변 문구가 아니라 입력 nonce와 결과 파일/세션 연속성을 판정한다. 실제 하드 한도·유료 전환의 관측이 없으면 fixture 검증으로만 보고한다.

## 9. 삭제·사용 중지·재설치 시나리오

삭제 범위를 구분한다. `aam deactivate`는 연결 해제이고 앱 제거가 아니다. 정상 제거는 계정·프로필·로그를 보존한다. 전체 데이터 purge 기능을 새로 만드는 것은 이 계획의 범위가 아니다.

| ID | 시나리오 | 합격 기준 |
|---|---|---|
| R01 | `aam deactivate --dry-run` | 계획만 출력, 파일/설정/프로세스 변경 없음; 서비스가 살아 있는 각 lease 상태에서 dry-run과 실제 차단 판정 일치 |
| R02 | idle 상태의 연결 해제 | admission 차단 → bridge/broker/observer → shell/shim → service 순서의 실제 효과, 원본 세 도구 정상 복귀 |
| R03 | PREPARED/STARTING/ACTIVE/SUSPECT/ORPHANED 각각 보유 | 사용 중지·삭제 거절, 실행 파일/설정·세션·자식 프로세스 보존 |
| R04 | 활성 omp 스트림·queued 요청 중 제거 시도 | §1.9의 정적 보호 공백을 먼저 재현; native lease 부재를 안전 근거로 사용하지 않음. 신규 admission 차단과 활동 확인 사이 경합에도 입력 유실/unknown 자동 재전송 없음 |
| R05 | bridge/역할 복원·shell/shim 제거 중 실패 | 실패 단계별 전후 상태표와 실제 상태 일치; 이미 끝낸 단계를 자동 원복한다고 가정하지 않음. admission 재개 RPC 실패도 주입해 허위 재개 안내 검출, 원인 해소 후 재실행의 멱등성·일관 상태 확인 |
| R06 | 사용자가 수정한 역할/설정/확장·omp 미설치/미연결 | 사용자 변경 보존, 연결 흔적 없으면 불필요한 omp 호출 없음, 충돌 시 증거 보존 |
| R07 | Mac `install.sh --uninstall` 및 system 설치 제거, Windows 설정→앱 제거 | Ojak 소유 앱·서비스 등록·shim/PATH만 제거; 원본 CLI·사용자 로그인·프로필·로그 유지 |
| R08 | 제거 도중 설치기/helper 종료·Windows 파일 잠금·동시 제거/업데이트 | 잠금·복구 기록 유지, 다른 프로세스 강제 종료 없음, 재시도 시 잘못된 파일 삭제 없음 |
| R09 | Ojak 앱을 직접 휴지통으로 이동/수동 삭제 | 잔여 서비스·shim을 완료로 오인하지 않음, 문서화된 복구/재설치/정상 제거로 복귀; 자동 정리 기능을 가정하지 않음 |
| R10 | 제거 후 새 셸·새 omp 세션·OS 재부팅·동일/새 버전 재설치 | 죽은 Ojak broker/경로 참조 없음, 원본 정상 실행, 보존 데이터 재연결·중복 등록 방지 |
| R11 | Claude/Codex/omp 자체를 먼저 제거 후 Ojak 해제·재설치 | 없는 CLI를 실행해 성공 처리하지 않음, 남은 사용자 설정/인증 보존, 복구 경로 안내 |
| R12 | 서비스 다운 + DB 점유 lease/살아 있는 native 자식/손상된 종료 근거 | permit 부재와 dry-run의 busy=0을 안전 근거로 삼지 않음. 실제 실행·소유 데이터 보호, 부분 해제 후 마지막 단계 거절 시 그 상태를 명시; 사전 차단이 필요한 보호 공백은 결함으로 기록 |

R05의 중간 상태는 `deactivate.rs`의 실제 단계 순서를 기준으로 기록한다. 예를 들어 shell 단계 실패 시 bridge/broker/observer는 이미 해제됐을 수 있고, service 단계 실패 시 shell/shim까지 해제됐을 수 있다. 각 단계에서 사용자 변경을 덮지 않는 재실행과 서비스가 재기동하는 경합을 함께 확인한다. 운영 복구 중 이런 부분 상태가 발생하지 않는다고 미리 가정하지 않는다.

## 11. 장애 주입과 관측 설계

- 고정 sleep에 의존하지 않고 `queued fsync 완료`, `starting 승인`, `요청 본문 수신`, `첫 응답`, `done 수신`, `completed 저장` 등 실제 경계에 barrier를 둔다. 제품 런타임의 임의 kill 스위치 대신 테스트 전용 transport/파일 시스템/프로세스 harness를 우선한다.
- 연결 거절은 열린 적 없는/닫힌 listener, 전송 불명은 실제 요청 수신 후 disconnect, 스트림 중단은 일부 응답 후 close로 구분한다. HTTP 응답 자체가 없었던 경우와 오류 응답을 혼동하지 않는다.
- 저장 실패는 임시 DB/프로필 또는 크기 제한 테스트 볼륨에서만 주입한다. 호스트 디스크 전체를 채우거나 운영 파일 권한을 바꾸지 않는다.
- 프로세스 강제 종료는 테스트 run이 소유한 PID+birth identity/Windows Job으로만 한다. 이름으로 kill하거나 실서비스를 kickstart하지 않는다.
- side-effect oracle은 임시 저장소의 nonce별 파일 작업 ledger, 수신 서버의 요청 수·단계, native spawn 수, lease/journal readback을 사용한다. 단순한 mock 반환값·호출 여부만 검사하지 않는다.
- 상태기계 기반 검증은 실제 lease/admission 전이에 대해 생성한 이벤트 순서와 고정 seed를 사용한다. 최종 결과 단일성·잘못된 자동 재전송 부재·타 세션 불변을 확인하고 실패 seed를 보존한다.
- 장시간 검증은 성능 측정과 분리해 낮은 빈도의 실행/취소/재시작을 반복한다. 자원 정리 마감과 허용 RSS 편차는 warm-up 기준선 후 실행 전에 고정하고, 결과를 보고 임계값을 느슨하게 바꾸지 않는다.

각 결과 행에 `scenarioId`, OS/build, Ojak/omp/공식 CLI/호스트 버전·해시, 증거 등급, fixture/live 여부, seed, 기대/실제 코드·상태, 전송·spawn·도구 실행 횟수, 전후 설정 비교, 결과(`PASS/FAIL/BLOCKED/NOT_RUN`), 안전한 증거 경로를 남긴다. 비밀을 포함한 설정/인증 파일 자체는 artifact로 저장하지 않는다.

## 12. 구현·실행 순서와 종료 기준

1. **범위 고정:** 실행 시 실제 버전/설치 채널 inventory, 시나리오별 OS·등급·선행 조건·실행 명령을 확정한다. Claude native/Homebrew·Codex standalone/npm/Homebrew 등 발견한 채널을 구분하고 지원하지 않는 조합은 명시한다.
2. **격리 기반:** 기존 harness 재사용, VM/전용 호스트 snapshot, 안전한 barrier·관측·보고 형식 구성. 운영 경로/포트/인증으로 연결되면 실패하는 사전 점검부터 만든다.
3. **최초 도입·핵심 안전 게이트:** 사용자 흐름은 J01 → J02 → J11 → J08 순서로 검증한다. 그 흐름의 실패 경계인 O06/O08/O11의 실제 pi-native, C09/X11의 spawn/lease 불명, R03/R04/R12/U03의 사용 중 보호, R05/U06의 중단·복구를 함께 먼저 실행한다. 제품 수정 시 failing-before/passing-after 증거를 남긴다.
4. **세 도구 정상·정책·복구:** O/C/X 전체에서 적용 가능한 A/B를 수행하고 네이티브 앱에서 연결·배정·오류·복구 상태를 확인한다. 그다음 승인된 C 검증으로 J03/J04/J05/J06/J09/J10을 완료한다. 공식 CLI를 대역으로 실행한 결과는 C로 올리지 않는다.
5. **설치 생명주기:** I/R/U 전체의 OS별 적용 케이스를 실제 패키지로 수행하고 J07/J12를 완료한다. 각 설치·업데이트·재설치 직후 세 도구 smoke를 다시 수행한다. 비밀 없는 clean snapshot으로 독립 실행한다.
6. **CI 배치:** PR에는 결정적 A와 실제 로컬 프로세스 B 핵심 시나리오, 예약 실행에는 경합·장시간·클라이언트 호환성, 릴리스 후보에는 실제 OS 패키지/로그인/서명 D 검증을 둔다. 기존 runner/명령을 확장하고 별도의 중복 프레임워크는 만들지 않는다.
7. **출시 판정:** 필수 케이스 FAIL/BLOCKED/NOT_RUN이 있으면 전체 통과라고 하지 않는다. 누락을 임의 제외하지 않고 사용자에게 해당 OS/기능 범위의 보류 또는 명시적 예외를 요청한다. 제품 변경은 기존 버전 정책에 따라 버전을 올린다.

기존 회귀 명령(향후 실행, 이 계획 작성 중에는 실행하지 않음):
```sh
~/.cargo/bin/cargo test --workspace --exclude ai-account-manager -- --test-threads=1
npm run typecheck
npm run test:desktop
node --test integrations/omp/aam-accounts.test.mjs integrations/omp/aam-observer.test.mjs
node --test scripts/install-sh.test.mjs
```
Windows 설치기 검증은 `powershell -NoProfile -File tests/install-ps1.tests.ps1`, 전체 unsigned CI 패키지는 `node scripts/build.mjs --verify-build`의 기존 CI 이벤트 제약을 따른다. 이는 실제 서명·설치·공개 업데이트 성공을 대신하지 않는다.

출시 보고는 반드시 분리한다: Mac 검증/설치, Windows 검증/설치, 공식 CLI 실제 공급자 검증, omp/Orca 호환성, 서명 후보 직접 설치, 공개 릴리스, 공개 후 앱 안 업데이트. 재빌드한 다른 바이트를 이미 검증한 후보로 취급하지 않는다.

### 실행 항목과 결과의 관리

- 실행 담당자는 각 기술 ID를 `OS / 설치 채널 / 시작 상태 / 장애 시점 / 증거 등급`으로 펼친 실행 목록을 만든다. 계정·한도·취소·설치 중단의 위험 경계는 조합 축소 없이 확인한다. 그 밖의 중복 환경은 pairwise로 줄이더라도 어떤 조합을 생략했는지 기록한다.
- 모든 실행 항목은 시작 전 준비 상태, 자극/조작, 관측 지점, 기대 결과, 복구/정리 방법을 갖춰야 한다. 실제 명령은 고정된 해당 버전 도움말/계약을 기준으로 작성하며 운영 PC 대상으로 실행하지 않는다.
- `PASS`는 요구 등급의 직접 증거가 있는 경우, `FAIL`은 계약 위반을 관측한 경우, `BLOCKED`는 환경·인증·승인 등 선행 조건이 없는 경우, `NOT_RUN`은 미실행이다. OS 전용 케이스의 반대 OS는 근거를 남긴 `N/A`이며 통과 건수에 넣지 않는다. 일시적 flaky 실패를 재실행 성공으로 지우지 않는다.
- 사용자 여정은 연결된 기술 케이스뿐 아니라 그 순서대로 수행한 종단 결과가 있어야 PASS다. fixture 검증만 끝난 한도·유료 전환은 실공급자 완료로 표시하지 않는다.
- **하드 차단:** 중복 실행, 잘못된 identity/프로젝트 실행, 인증 우회·비밀 노출, 사용자 데이터 훼손, 사용 중 작업의 무단 종료를 관측하면 해당 후보를 중단한다. 다른 통과 건수로 상쇄하지 않는다.
- **출시 전:** 두 OS의 적용 가능한 필수 케이스와 직접 설치 게이트를 통과해야 한다. 예외는 사용자가 명시적으로 범위·위험을 승인한 경우에만 별도 기록하며 전체 통과라고 부르지 않는다. 공개 후에만 가능한 앱 안 업데이트(U13)는 사전에 절차를 확정하고 공개 직후 별도 확인한다.
- **공개 후:** 앱 안 업데이트 실패는 기존 릴리스 정책의 보존·다음 patch 절차를 따른다. 검증 실패를 숨기기 위해 태그나 같은 버전의 산출물을 바꾸지 않는다.

### 작업 산출물

1. 기존 suite에 통합된 consumer-visible 회귀 테스트와 양 OS 실행 도구.
2. 후보 버전/해시가 고정된 실행 목록과 OS별 결과표, 사용자 여정별 결과표.
3. nonce별 요청·spawn·실제 파일 결과 및 안전한 상태 증거. 인증 자료/원문 대화/덤프는 자동 업로드하지 않는다.
4. 결함별 재현 조건·실패 단계·영향 범위·수정 전후 증거, 남은 BLOCKED/NOT_RUN 사유.
5. 문서화한 설치·복구·업데이트·제거 안내와 Mac/Windows/공개 상태를 분리한 릴리스 판정.

## 13. 계획 단계에서 확정하지 않은 실행 전제

- `windows-pc`는 SSH 접속 및 `Microsoft Windows NT 10.0.26200.0`·`AMD64`를 읽기 전용으로 확인했다. 기존 사용자 운영 PC이므로 전용 테스트 호스트로 취급하지 않는다. 격리 검토를 통과한 임시 checkout의 A 등급 테스트가 우선이며, 실제 CLI/omp 실행은 live 서비스·계정을 사용할 수 있어 별도 승인이 필요하다. 설치·삭제·업데이트·강제 종료 검증은 별도 Windows VM/전용 호스트가 기본이다. 같은 PC의 별도 사용자만으로는 고정 TCP 포트가 격리되지 않는다. `--verify-build`는 기존 CI 이벤트 제약을 유지한다.
- 전용 Mac/Windows 테스트 환경 및 최소 지원 OS 실행 가능 여부는 아직 확보·검증하지 않았다. 운영 Windows 접속 성공은 이 조건 충족을 뜻하지 않는다.
- 테스트 전용 계정·공식 OAuth 사용자 승인·실모델 호출 예산은 실행 단계의 승인 대상이다.
- 실제 공급자의 하드 한도 및 유료 fallback은 fixture만으로 실계정 동작을 보장할 수 없다. 한도 소진/과금 유발을 기본 테스트에 넣지 않는다.
- 서명키는 기존 release workflow의 비밀 경계를 유지한다. draft/태그/공개/운영 설치 변경은 별도 승인·릴리스 정책을 따른다.
- 현재 계획은 문서 작성만 수행한다. 제품 코드·CLI 설치·운영 서비스·인증·사용자 설정·브랜치를 변경하지 않는다.

## 14. 계획 검토 기록

- 두 읽기 전용 조사로 omp와 native CLI의 기존 코드/테스트 계약을 수집했다. 조사자의 미검증 주장(예: 무조건 즉시 슬롯 반환, 외부 공급자 과금 완전 차단)은 채택하지 않았다.
- advisor 자동 검토는 인증/문서 접근 문제로 유효한 파일 검토 결과를 확보하지 못했다. 이를 통과로 집계하지 않았다.
- 별도 Claude read-only 검토에서 제안한 bridge 활동 보호 공백, 서비스 다운 제거 경로, 부분 해제 상태, dry-run 일관성, Windows x64 환경 및 업데이트 거절 조건을 직접 코드/문서와 대조해 반영했다.
- 최소 지원 OS는 CONTRIBUTING.md에 명시돼 있음을 확인했다. dry-run과 service의 점유 상태 집합은 현재 동일하지만 향후 회귀 검증 대상으로 유지한다. 실제 시나리오 실행이나 결함 수정 완료를 뜻하지 않는다.
- 최종본에는 사용자 여정 J01–J12, 작업 중 최초 설치 I11–I16, 최초 도입 인증 충돌 I17, Windows 보안 경고 I18을 반영했다. 최종 범위는 사용자 여정 12개와 기술 시나리오 87개이며, 시나리오 추가는 실제 검증 완료를 뜻하지 않는다.
