# 초기화권을 조용히 챙기는 업무 연속성 기능

## 1. 쉽게 보는 제품 방향

**일은 최대한 이어가고, 쿠폰은 오작이 챙기되 쓰기 전에는 반드시 묻습니다. 다른 일을 하고 있으면 창을 띄우지 않습니다.**

- 새 업무를 배정할 때 곧 만료될 쿠폰을 활용할 수 있는 계정을 고려합니다. 진행 중인 업무를 쿠폰 때문에 옮기지 않습니다.
- 쿠폰을 쓸 시점에는 조용히 표시만 합니다. 사용자가 직접 확인 화면을 열고 동의해야 한 장을 씁니다.
- 답이 없으면 쿠폰은 쓰지 않습니다. 다른 계정으로 안전하게 이어갈 수 있으면 기존 전환 규칙대로 진행합니다.
- 아무 일도 없을 때 쿠폰을 위해 계속 조회하거나 PC를 깨우지 않습니다.
- 목표는 쿠폰 소진율 자체가 아니라 작업 보존·대기 감소·유용한 쿠폰 사용입니다. 무조건 무중단·만료 방지 100%를 약속하지 않습니다.

### 확정한 사용자 요구와 범위

사용자는 저부하 동작, 매번 사용 확인, 다른 업무 중 갑작스러운 팝업 금지, 사용자 시나리오 중심 검증을 승인했습니다. 앞서 논의한 사전 동의형 자동 소비는 **폐기**합니다. 이번 요청은 스펙 작성이며 제품 코드·운영 설정·실계정 쿠폰·릴리스를 변경하지 않습니다. 구현 브랜치는 지금 전환하지 않으며 진행 중인 0.16.4 배포 후보에 섞지 않습니다.

범위: macOS/Windows의 Ojak 데스크톱·메뉴바/트레이, omp 호환 확장, Ojak 관리 Claude Code/Codex, 서비스의 쿠폰 조회·배정·승인 경로. 비관리 CLI에 화면이나 입력을 주입하지 않습니다.

범위 밖: AI 예측, 별도 상주 프로세스, 유료 사용 자동 활성화, 강제 로그아웃/계정 교체, 자동 프롬프트 재실행, 새 CLI 대화형 승인 TUI, PC 간 승인 동기화 서버.

현재 코드상 Codex와 Claude Juniper는 `requires_limit=true`입니다. Cedar는 공급자 `use_requires_limit`을 읽으며 없으면 true입니다. 이는 정규화 코드 확인이지 모든 실제 계정의 공급자 응답을 검증했다는 뜻이 아닙니다. `usable`과 `requires_limit`은 별개이며, usable만 보고 한도 전 소비가 허용된다고 추측하지 않습니다.

현재 `reset_begin`/`canUseReset`은 `usable`·수량·quote 등을 검사하지만 **로컬 한도 소진과 `clears`의 차단 해소를 직접 판정하지는 않습니다**. §8의 scope/소진 검사는 이번 구현에서 추가할 계약이며 기존에 완료됐다고 간주하지 않습니다.

| 프로그램 | 기간·사용 조건 해석 | 안내·배정 적용 |
|---|---|---|
| Codex rate-limit credit | `expires_at`가 있는 개별 credit, `requires_limit=true` | 확인된 만료만 만료 기준 사용. 없는 시각은 추정하지 않음 |
| Claude Cedar | `ends_at`/`starts_at`, `next_grant_id`, `usable_now`, cooldown, `use_requires_limit` | 현재 공급자 순서상 대상만 추천. 순서에 막힌 grant는 목록에서 이유를 보이고 선택 불가 |
| Claude Juniper | 고정 ID, `weekly_resets_at`가 현재 `expires_at`로 정규화됨, 5h만 초기화, `next_available_at` 조건 | 주기 종료를 영구 쿠폰 손실로 표현하지 않음. 만료 우선 배정에서 제외하고 실제 한도 소진·사용 가능 시 안내 및 수동 확인 제공 |

안내용 기간 의미는 `expiryKind: expires | cycle_end | unknown`으로 구분합니다. 원본 정규화 값은 보존하되 프로그램별 의미를 UI에 반영합니다. Juniper가 다음 주에 반드시 재지급된다고 보장하지 않습니다.

기존 `expiringBoost`/`expiringWindowHours`는 **구독 한도의 자연 리셋** 정책입니다. 쿠폰 만료와 같은 값으로 덮어쓰거나 의미를 바꾸지 않습니다.

## 3. 영향도와 선택한 방향

| 영역 | 점수(0–5) | 근거 |
|---|---|---|
| 코드 | 4 | protocol/service/desktop/omp/launcher 연결 |
| 실행·성능 | 3 | 캐시, 단일 조회 작업, 배정 경로의 무 I/O 보장 |
| 사용성 | 4 | 승인과 업무 진행 분리, 세 도구의 서로 다른 표면 |
| 데이터 | 2 | 안내/미루기 상태와 계정 정책 저장; 기존 소비 기록 재사용 |
| 외부 연동 | 3 | 공급자별 조건, 앱 활성화와 원격/다중 PC 제약 |
| 검증 | 4 | OS×도구, 중복 승인·통신 장애·포커스·성능 |

검토한 선택지: (A) 수동 조회만 유지하면 저부하이나 만료 안내가 부족합니다. (B) 상시 감시·자동 소비는 사용자 요구에 어긋납니다. **(C) 기존 업무 이벤트에서 캐시 기반 안내/배정 + 사용자가 연 승인 화면**을 선택합니다. 사용자와 이미 합의한 방향이므로 다시 선택을 요구하지 않습니다.

## 4. 화면별 사용자 경험

| 표면 | 자동으로 가능한 안내 | 사용자가 확인하는 방법 | 응답이 없을 때 |
|---|---|---|---|
| Ojak 창이 뒤에 있거나 닫힘 | 기존 메뉴바/트레이에 정적인 확인 필요 표시. 새 창·소리·OS toast·깜박임·Dock bounce 없음 | 사용자가 아이콘/메뉴를 눌러 쿠폰 목록을 열고 항목 선택 | 소비 없음. 작업 대기열을 승인 때문에 붙잡지 않음 |
| Ojak 사용 현황을 보고 있음 | 기존 레이아웃의 쿠폰 안내 영역에 내용 갱신. 자동 모달·스크롤 이동 없음 | `확인하기` → 계정별 기존 패널 | 닫거나 무시해도 진행 중 작업 유지 |
| omp | 현재 Ojak 세션의 작은 상태 영역만 사용. `select`/`confirm` 자동 호출 금지 | 명시 명령 `ojak-coupons`로 읽기 전용 요약; 소비는 사용자가 Ojak에서 확인 | 지원되는 기존 전환/대기 동작 유지. 상태가 없어도 작업을 막지 않음 |
| 관리 Claude Code/Codex | 원본 CLI가 실행 중이면 별도 출력/입력 가로채기 없음. 한도 때문에 최종 종료하고 TTY를 반환한 경우에만 stderr 한 줄 안내 | 사용자가 Ojak을 직접 열어 확인 | 기존 안전 전환 또는 기존 한도 종료. handoff 도중에는 새 CLI 화면에 묻힐 별도 안내를 삽입하지 않음 |
| 비TTY·중첩·원격 CLI | 팝업·stdin 읽기·자동 데스크톱 실행 없음. stdout 결과 형식 변경 없음 | 관리 호스트의 Ojak에서 직접 확인 | 기존 종료/전환 규칙. 새 자동 재개 보장 없음 |

`ojak-coupons`와 쿠폰 전용 메뉴/상태는 **새로 구현할 인터페이스**입니다. 기존에 있다고 가정하지 않습니다. omp가 해당 호스트의 Ojak에 연결돼 있지 않으면 명령은 연결 필요만 알리고 로컬의 다른 Ojak을 조작하지 않습니다. headless/확장 UI 미지원이면 요약 조회만 제공하며 소비 버튼을 흉내 내지 않습니다.

메뉴바/트레이 표시는 OS 알림 권한을 우회하는 가짜 notification badge가 아니라 앱 자체 상태 표시입니다. 개인정보 모드와 무관하게 툴팁/상태 영역에는 이메일·워크스페이스·프로젝트·쿠폰 ID를 넣지 않습니다. 도구별 호환성과 OS 표시는 실제 실행 검증이 필요합니다.

Mac은 기존 `set_title`의 잔여 한도 표시를 덮지 않게 조합하고, Windows는 `set_title`이 효과 없으므로 정적인 아이콘 상태+툴팁+메뉴 항목으로 표현합니다(`main.rs:2076-2101`). 두 OS 모두 기존 클릭 팝오버(`main.rs:2518-2544`)를 진입점으로 씁니다. `show_main`은 사용자의 직접 클릭에서만 허용합니다. 앱을 완전히 종료하면 트레이 안내도 없으며 서비스가 앱을 다시 실행하지 않습니다. 기존 자연 리셋 OS 알림 설정은 이번 기능에서 자동 변경하지 않고 쿠폰 이벤트를 그 알림 경로에 넣지 않습니다.

omp는 admission과 다른 `ojak-coupons` status key를 씁니다. 새 반복 polling은 만들지 않습니다. 기존 admission 응답에 Ojak 인증 경계 안의 개인정보 없는 `{noticeRevision, noticeCount}` 선택 필드를 붙이고, 그 응답을 실제 받는 시점에만 상태를 갱신합니다. 요청마다 쿠폰 목록을 가져오지 않습니다. 명시 명령만 로컬 서비스 `resetCredits.notices`를 조회하며 종료/cancel/재연결 때 오래된 상태를 지웁니다. 구형 응답에 필드가 없으면 쿠폰 상태를 표시하지 않을 뿐 기존 admission은 유지합니다. 이 추가 필드는 예약·승인·권한을 부여하지 않습니다.

안내는 **정보 안내**(`만료 예정, 아직 사용 조건 아님`)와 **사용 검토 가능**(`한도 소진, 초기화 가능`)을 구분합니다. 정보 안내를 보고 연 화면에는 사용 불가 이유·자연 회복 시각·`나중에`가 있어야 하고, 사용 버튼을 유효한 것처럼 보이지 않습니다. 사용 검토 가능 판정도 승인용 fresh quote를 대신하지 않습니다.

한도 최종 종료 시 launcher의 로컬 안내 조회는 총 200ms deadline으로 제한하고 실패하면 기존 종료만 수행합니다. 미룬 쿠폰을 다시 특정해서 재촉하지 않으며, 필요한 경우 기존 한도 오류의 일반적인 수동 복구 경로만 남깁니다. handoff 성공 중에는 추가 조회하지 않습니다.

### 사용자가 직접 여는 확인 화면

1. 계정 표시 이름, 공급자, 선택된 쿠폰, 만료 시각, 초기화 대상, 현재 해당 한도와 자연 회복 시각을 표시합니다. 미확인은 미확인으로 씁니다.
2. `이 쿠폰 1장을 사용합니다` 확인란은 기본 해제이며 자동 focus/Enter 기본 승인 없음. `사용`과 `나중에`를 제공합니다.
3. `확인하기`는 조회/상세 진입이지 사용 승인이 아닙니다. 목록 클릭이나 창 열기만으로 소비하지 않습니다.
4. 사용자 클릭으로 확인 화면에 진입할 때만 fresh quote를 요청합니다. 표시 중인 quote의 만료 시각에 **화면 수명 내 단발 타이머 한 개**로 사용 버튼/동의를 해제하고 `다시 확인`을 제공합니다. 숨김/닫힘 때 타이머를 해제하고 복귀·클릭 시에도 시간을 다시 검사합니다. 2분마다 자동 재조회하지 않습니다. 쿠폰·계정·범위·수량·사용 조건이 바뀌어도 다시 동의받습니다. 다른 창에서 새 quote가 발급돼 기존 quote가 교체된 경우에는 명확한 재확인 안내 후 소비하지 않습니다.
5. `사용` 클릭 뒤 중복 클릭 차단. 화면은 `사용 확인 중`으로 바뀌며 다시 사용 버튼을 만들지 않습니다.
6. 성공 응답만으로 `작업 재개 완료`라고 하지 않습니다. 한도 회복과 실제 작업 재개는 별도 상태입니다.
7. 실행 중 닫기는 제출 취소를 뜻하지 않습니다. 다시 열면 기존 request ID 결과를 읽으며 POST를 다시 만들지 않습니다.
8. 앱이 없는 원격 환경에서는 소비 불가를 분명히 알립니다. 숨은 TTY 질문이나 브라우저 자동 실행으로 대체하지 않습니다.

### 미루기와 중복 안내

- `나중에`: 그 **계정의 해당 쿠폰 주기**를 읽음/미루기로 저장하고, 새 알림 표시와 해당 쿠폰의 배정 가산점을 없앱니다. 만료가 더 가까워져도 다시 재촉하지 않습니다.
- 사용자가 목록을 열면 미룬 항목도 볼 수 있고 `다시 챙기기`로 명시 해제할 수 있습니다. 미루기는 나머지 쿠폰을 모두 숨기거나 동의를 저장하는 기능이 아닙니다.
- 단순 목록 열기는 읽음 처리만 합니다. 선택하지 않은 쿠폰을 미뤘다고 간주하지 않습니다.
- 안내 키는 물리 계정+프로그램+쿠폰 식별자+공급자 주기/만료입니다. quote UUID나 관측 시각은 키가 아닙니다. 별칭/여러 창은 같은 키를 사용합니다.
- 동일 ID의 새 주기 여부를 확인할 수 없으면 이전 미루기를 자동 해제하지 않습니다. 명시 갱신 후 확정된 새 주기만 새 안내입니다.
- 만료·소진·삭제는 안내 대상에서 제거합니다. 일시 조회 실패는 `확인 필요`로 바꾸되 새 안내로 폭증시키지 않습니다.
- 여러 쿠폰은 합산 안내 한 개와 목록으로 표시합니다. 사용은 반드시 개별 선택·개별 승인입니다.
- 미룬 뒤 실제 한도 소진이 발생해도 **같은 쿠폰으로 트레이/omp의 새 미확인 알림을 다시 만들지 않습니다**. 사용자 의도를 지키기 위해서입니다. 다만 사용자가 보는 해당 작업의 기존 한도 오류 상세/쿠폰 목록에는 현재 사용 가능 여부와 수동 확인 경로가 남습니다. 그 정보는 반복 popup이 아니며 미루기를 자동 취소하지 않습니다.

## 5. 배정 규칙: 업무를 방해하지 않는 선에서만

설정 `쿠폰 챙기기`는 기본 꺼짐, 사용자가 켜면 안내와 조건부 새 업무 우선 배정을 활성화합니다. 설정 설명에 **자동 사용은 하지 않고, 사용할 때마다 확인한다**고 적습니다. 끄면 background 조회·쿠폰 가산점·상태 안내를 중단하되 소비 진행/unknown 기록은 보존합니다. 기존 수동 패널은 유지합니다.

배정 순서:

1. 기존 보안/인증/프로젝트 허용 범위·모델 지원·slot·신선도·한도 조건을 통과한 후보만 사용합니다.
2. 진행 중 대화 sticky, resume/parent 고정, 수동 선택, 명시 순서 모드는 유지합니다. 예외를 새로 만들지 않습니다.
3. 스마트 배정의 **새 작업**에서만 비교합니다. 현재 사용 가능한 기본 한도가 있어야 하며, 쿠폰이 있다는 이유로 소진 계정을 eligible로 만들지 않습니다.
4. 기존 안전 여유량·자연 리셋 우선 그룹·plan 선택 순서를 유지하고 그 안에서 만료 예정 쿠폰을 우선 비교한 뒤 기존 점수를 사용합니다(`scheduler.rs:505-570`). 쿠폰이 모델/도구에 해당하지 않거나 다른 미해결 한도를 풀지 못하면 가산점 없음.
5. 대상은 `expiryKind=expires`, 기본 24시간 이내 만료, 15분 이내 신선한 inventory, 공급자 `usable=true`, 남은 수량 있음, 해당 주기가 미뤄지지 않음, 미확정 소비 없음입니다. starts/cooldown 등 조건을 확인하지 못한 쿠폰을 유효한 회복 수단으로 가산하지 않습니다. usable이 소진 전 false인 프로그램에는 선제 가산점을 주지 않으며 존재하지 않는 자격을 추정하지 않습니다.
6. `requires_limit` 쿠폰을 활용하려고 실제 필요한 새 업무만 배정합니다. 한도를 소진시키기 위한 인공 요청·모델 변경·병렬 작업 증설은 금지합니다. 실제 소비 가능 조건은 매번 별도 확인합니다.
7. 승인 대기 쿠폰은 **확보된 잔여 한도/회복 보장**으로 계산하지 않습니다. 현재 실행 가능한 다른 계정과 기존 여유량 기준이 우선입니다.
8. 신선한 조건을 만족하는 쿠폰끼리는 먼저 만료되는 순서, 이후 기존 점수를 사용합니다. 공급자가 `next_grant_id`로 정한 소비 순서는 바꾸지 않습니다.

정확한 소진 시각 예측은 하지 않습니다. 기본 24시간은 제품 초기값이지 공급자 보장이나 실측 최적값이 아닙니다. expiry 미제공 쿠폰은 수동 목록에는 보이지만 만료 가산점/만료 안내 대상에서는 제외합니다.

가산점은 **현재 실행 가능한 실제 업무의 목적지만 선택**하는 기능입니다. 한도 소진은 승인·회복 기회의 보장도 목표도 아닙니다. 공급자가 소진 뒤에만 usable을 준다면 소진 시 수동 회복 안내만 가능하다는 한계를 표시합니다.

우선 배정은 **이미 신선한 관측이 있는 계정 사이에서만** 보장합니다. 15분 넘게 사용/조회하지 않은 계정을 발견하려고 배정을 멈추거나 전체 계정을 훑지 않습니다. 관측이 없으면 기존 배정으로 돌아갑니다. 이 탐지 공백은 저부하를 위한 의도된 제한입니다.

## 6. 한도에 걸렸을 때와 승인 뒤 작업

- 다른 계정으로 안전하게 이어갈 수 있으면 기존 handoff/bridge 경계를 따릅니다. 쿠폰 승인 때문에 별도 대기시키지 않습니다.
- 다른 계정이 없으면 기존 한도 안내/종료/미전송 대기 정책을 유지하고 수동 쿠폰 확인 경로만 제공합니다. 무기한 승인 큐를 추가하지 않습니다.
- 승인 후 원래 작업이 이미 다른 계정으로 이동했으면 다시 끌어오지 않습니다. 쿠폰으로 회복된 계정은 이후 신규 배정에 사용합니다.
- 승인 후 **아직 전송하지 않은** 요청이 기존 대기 경로에 있으면 그 경로의 조건을 재평가할 수 있습니다. 이를 위해 이미 끝난 세션을 자동 생성하지 않습니다.
- `BRIDGE_EXECUTION_UNKNOWN` 등 완료 불명 요청은 쿠폰 성공과 무관하게 재전송 금지입니다. 입력 보존과 실행 재개는 구분합니다.
- Claude Code/Codex의 같은 계정 자동 재개는 기존 `continue_elsewhere`로 대체하거나 지원한다고 주장하지 않습니다. 이번 기능은 계정을 회복시킨 뒤 기존 도구의 명시 재개 안내를 제공합니다. 동일 계정 자동 재개가 필요하면 별도 계약·공식 CLI 실기 검증 후 별도 변경으로 다룹니다.
- 쿠폰 성공 뒤 새 한도 조회에서 다른 차단이 남으면 `쿠폰은 사용됐지만 이 한도는 아직 사용할 수 없음`을 보여줍니다. 다른 한도·lease·속도 제한을 임의로 해제하지 않습니다.

앱을 오래 열어두는 것만으로 추가 조회하지 않습니다. 기존 snapshot 갱신에서 로컬 시간/신선도를 반영하고 `다시 조회`를 제공합니다. 기존 polling에서 창 상태를 구별할 수 없다면 이를 근거로 자동 조회를 시작하지 않습니다.

현재 `resetCredits.read(refresh:false)`는 quote 저장소를 읽고 5분 뒤 수량을 unknown으로 바꿉니다(`reset_credits.rs:109-127`). 구현에서는 **관측 저장소와 승인 quote 저장소를 분리**합니다. 물리 계정 owner+binding 세대별 `resetObservation`에 최신 inventory·관측시각·후속 operation 세대를 저장하고 메모리에 같은 projection을 유지합니다. 안내와 패널의 수량 표시 신선도는 둘 다 15분으로 통일하되 quote는 2분을 유지합니다. stale일 때 마지막 관측 사실과 현재 미확인을 구분합니다. 기존 저장 quote가 유효한 binding/세대이면 최초에 observation으로 옮길 수 있으나 관측 시각을 현재로 바꾸지 않습니다.

명시 조회도 observation을 갱신하고, 그 명시 요청에만 quote를 발급합니다. 자동 조회는 quote를 만들거나 교체하지 않습니다. 승인 진행 중 안내 조회를 뒤로 미루며 POST 직전 fresh 검사는 유지합니다. 자동 관측에서 조건 변경이 확인되면 UI의 기존 동의는 무효화할 수 있지만 무변경 갱신마다 초기화하지 않습니다. `refresh:false`는 저장된 결과만 읽고 새 quote를 발급하지 않습니다.

현재 `reset_credential`은 `ready()`를 호출해 인증 subprocess가 생길 수 있으므로(`bridge_native.rs:640-653`) 자동 조회에 그대로 쓰지 않습니다. 기존 source의 검증된 메모리 credential을 **갱신 없이** 읽는 내부 경로를 추가하며 expiry·identity·auth override·거절 상태 검사를 생략하지 않습니다. 준비된 credential이 없으면 자동 조회는 미확인으로 끝나고 명시 조회에서만 정상 인증 경로를 탑니다. 새 토큰 저장소/인증 우회/인증 실패 자동 수정을 만들지 않습니다.

Native credential은 기존 `FRESH_MS=30_000` 기준을 늘리지 않고 `0 <= now-checked_at < 30초`, 만료까지 60초 초과, rejected 아님, 현재 source의 identity/binding 세대 일치 및 `validate()` 성공을 모두 요구합니다. 확보된 source가 없으면 새 loader를 만들지 않습니다. 따라서 사용자가 한동안 쓰지 않은 native 계정은 자동 조회되지 않을 수 있습니다. omp OAuth는 정확한 identity를 선택하는 기존 broker snapshot의 읽기 전용 경로만 최대 한 번 사용하며, `/refresh` POST 분기는 자동 조회에서 금지합니다. snapshot이 모호/만료/실패이면 건너뜁니다. broker 로컬 GET 1회는 공급자 GET 최대 3회와 별도로 계측하며 유효 token을 디스크에 새로 저장하지 않습니다.

쿠폰 0장 관측은 자동 재조회 최소 6시간의 음성 캐시를 두고 명시 조회는 즉시 허용합니다. 미지원 공급자는 binding/지원 프로그램 변경 전 자동 재조회하지 않습니다. 둘 다 수량 확인 freshness를 6시간으로 늘리는 뜻은 아니며 stale이면 미확인입니다. 계정 삭제/비활성화/재로그인 시 큐·캐시를 무효화합니다. 30초 전역 간격으로 많은 계정을 15분마다 모두 최신으로 유지할 수 없으므로 그런 SLA를 약속하지 않습니다. 실제 작업/사용자 선택 대상만 큐에 넣고 큐는 등록 물리 계정 수를 넘지 않습니다.

## 8. 데이터·API·상태 계약

아래 새 이름은 구현 목표이며 현재 존재하는 RPC/필드로 오인하지 않습니다. schema/타입은 `crates/protocol`을 정본으로 하고 desktop에 별도 문자열 표를 만들지 않습니다.

- 정책: `couponAssistEnabled`(기본 false). 24시간 안내창·15분 freshness는 우선 내부 상수로 두어 설정을 늘리지 않습니다.
- 서비스 내부 안내 요약: `noticeKey`, 계정 binding, coupon reference, `expiryKind`, `expiresAt`, `observedAt`, `state`, `reason`, `readAt`, `deferred`, `eligibility: informational | actionable | unknown` 및 `gateState`/operation 세대. 배정에 필요한 gate projection은 redeem 진입·제출·완료·reconcile·재시작에서 원자적으로 무효화/갱신합니다. 미확인이면 가산점 없음. 소비 권한 판단은 여전히 durable gate가 정본입니다.
- `state`: `unseen` / `seen` / `deferred` / `inactive`. `reason`: `expiring` / `limit_reached` / `outcome_unknown`. 쿠폰 inventory의 known/unknown/unsupported와 소비 operation 상태는 별도로 둡니다.
- `resetCredits.notices`: 로컬 캐시만 읽는 요약 목록. quote 발급·외부 조회·소비 없음. 서비스 snapshot에는 개수와 변경 revision만 넣어 반복 전체 목록 전송을 피합니다.
- `noticeRevision`은 사용자에게 보이는 수량·조건·안내·읽음/미루기 상태가 바뀔 때만 증가합니다. 관측 timestamp 갱신만으로 변경하지 않습니다. `cycle_end`는 `expiring` 사유를 만들지 않고 실제 사용 가능 시 `limit_reached` 안내만 제공합니다.
- `resetCredits.noticeAction`: `seen` / `defer` / `restore`, `noticeKey`+binding/현재 주기 검사. stale action은 다른 쿠폰에 적용하지 않음. 절대 소비하지 않음.
- `resetCredits.read` / `resetCredits.redeem`: 기존 사용자 조회/승인 소비 경로 유지. 새 화면도 같은 redeem을 호출하고 `confirmed:false`/누락은 계속 거절합니다.
- 재시작 시 안내 요약은 저장 inventory에서 재구성하고 동의 체크는 복원하지 않습니다. backward clock/stale binding은 미확인으로 취급합니다.
- 안내 기록은 현재/미확정 주기만 보존하고 종료된 안내는 제거할 수 있습니다. **기존 request/gate 기록은 안내 청소로 삭제하지 않습니다.** 로그에는 원문 응답·토큰·이메일·쿠폰 원본 ID·프롬프트를 기록하지 않습니다.

데이터 흐름: 기존 활동/사용자 조회 → 단일 조회 작업 → 정규화 inventory/메모리 요약 → notice revision → desktop/tray/omp 표시 → 사용자의 직접 확인 → fresh quote → 기존 redeem 관문 → durable submitted → 공급자 POST → 결과 확인 → 한도 갱신 → 기존 배정.

### 소비 안전 조건

- 해당 계정·선택 쿠폰 한 장에 대한 명시 동의만 유효합니다. 미래 자동 소비·다른 계정·다른 쿠폰에 동의를 재사용하지 않습니다.
- `requires_limit`이면 신선한 적용 한도 소진과 공급자 eligibility를 확인합니다. 한도에 가까운 것만으로 허용하지 않습니다. quote 발급 때 관련 quota 관측이 2분보다 오래됐으면 명시 조회 흐름에서 그 계정의 사용량을 갱신하고, `reset_begin`과 POST 직전에도 2분 이내·현재 binding·아직 지나지 않은 자연 회복 시각을 확인합니다. 실패/미확인/회복됨이면 소비하지 않고 이유를 표시합니다. 조회 시간이 길어 quote가 만료되면 새 동의가 필요하며 TTL을 늘리지 않습니다.
- `clears`가 현재 blocking scope를 풀지 못하면 **업무 재개용 추천**을 하지 않습니다. `requires_limit=true`의 소비도 해당 소진을 풀어 실제 사용 가능해지는 경우만 허용합니다. 자연 회복이 먼저 됐으면 화면을 갱신하고 불필요한 소비를 진행하지 않습니다.
- `requires_limit=false`는 공급자가 현재 사용 가능하다고 확인한 경우 소진 전 **수동 사용**도 허용합니다. 현재 사용량·남은 한도·초기화 범위와 확인된 효과를 보여주고, 미사용 한도 이월/누적을 약속하지 않습니다. 자동 소비는 여전히 없으며 다른 한도가 막혀 있으면 업무가 재개된다고 표시하지 않습니다. 실제 사용량이나 효과가 미확인이면 사용 불가로 두고 조회를 안내합니다.
- 범위 매핑은 공유 함수로 단일화합니다. Claude는 정규화된 `anthropic:5h/7d/7d:opus/7d:sonnet`을 적용 모델 버킷과 대조합니다. Codex의 `openai-codex:rate_limits`는 `codex:{identity}:{scope}:{window}` 버킷 ID와 문자열 동등 비교하지 않습니다(`adapters/src/quota.rs:366`). 공급자 계약상 초기화되는 scope를 실제 응답/테스트로 확정하고, 알려지지 않은 scope는 전체 초기화로 취급하지 않습니다.
- scope 의미를 fixture와 승인된 실계정 자료로 확인하기 전 해당 프로그램은 안내/조회만 가능하며 actionable/회복 보장 가산점/소비를 활성화하지 않습니다. 특히 Codex aggregate scope를 모든 모델·모든 시간창 초기화로 임의 확장하지 않습니다. 이 지원 게이트는 문구 경고만으로 소비를 허용하는 방식으로 대체하지 않습니다.
- 조건을 확인하는 동안 달라진 offer/binding은 기존 변경 거절 경로로 끝내고 새 동의를 받습니다. 공급자 변경을 클라이언트만으로 완전히 봉쇄할 수 있다고 주장하지 않습니다.
- `submitted`/`unknown`은 같은 물리 계정의 다른 별칭에서도 소비 차단. restart·timeout·화면 재열기·버튼 재클릭으로 새 POST 금지.
- 불명 결과는 기존 read/reconcile로만 확인합니다. `resolved`는 자동으로 성공이나 업무 회복을 뜻하지 않습니다.
- PC 간 local gate는 공유되지 않습니다. 두 PC에서 같은 쿠폰을 동시에 사용했을 때 공급자 측 중복 방지가 검증되기 전에는 글로벌 exactly-once를 주장하지 않습니다. 확인 화면에 다른 기기에서도 같은 쿠폰을 사용 중이면 기다리도록 안내합니다. 별도 동기화 서버 없이 안전 보장을 과장하지 않습니다.

## 10. 검증 방법과 합격 기준

1. **결정 로직:** 기존 Rust 테스트 패턴으로 우선순위·제외조건·시간 경계·scope·미루기 전이를 검증합니다. 새 함수 존재/문구 고정 테스트는 만들지 않습니다.
2. **소비 경합:** 기존 loopback 공급자 fixture에서 quote 교체, 한도 회복, double-click, alias, POST 전/후 단절·restart를 주입하고 **실제 POST 횟수와 durable 상태**를 확인합니다.
3. **UI:** 기존 desktop 테스트로 선택·동의·취소·키보드·stale 상태의 실제 사용자 동작을 검사합니다. 버튼 연결을 mock echo로만 증명하지 않습니다.
4. **실행 표면:** 실제 pinned omp와 공식 CLI를 실제 TTY에서 실행하고 계정 한도 신호를 격리 fixture로 유발합니다. 사용자 입력 보존·프로세스 트리·안내 시점을 확인합니다. 원본 CLI 실계정 한도 소진 증거와 fixture는 구분합니다.
5. **네이티브 사용성:** Mac 메뉴바/Windows 트레이, 숨김/잠금/전체화면/다른 앱 타이핑에서 실제 foreground 창·focus·소리·알림·스크린샷을 확인합니다. 브라우저 모의 화면으로 이를 대체하지 않습니다.
6. **실계정 데이터 게이트:** 승인된 테스트 계정에서 프로그램·만료·starts/cooldown·clears·requires_limit·잔여량·관측시각 존재 여부를 비식별 기록합니다. 실제 쿠폰 소비는 사용자 개별 승인이 있어야 하며 fixture 결과를 실소비 성공으로 기록하지 않습니다.
7. **경량성:** 같은 OS/빌드/계정 수/작업으로 OFF/ON 각각 3회, idle 30분 및 새 배정 1,000회 비교. 기존 공급자 요청 비용과 추가 쿠폰 비용을 분리합니다. 제안 합격선: 단일 코어 기준 idle CPU 평균 증가 0.2%p 이하, 20계정·계정당 20쿠폰에서 안정 RSS 증가 10MiB 이하, 배정 p95 증가 2ms 이하. 네트워크/프로세스 예산은 §7을 엄격 적용합니다. Mac/Windows 각각 원시 측정과 p50/p95·최대값을 기록하며 측정 잡음이 크면 원인을 분리합니다.
8. **배포:** 두 OS의 전체 회귀와 동일 서명 산출물 설치/업데이트 검증은 `docs/release-policy.md` 준수. 새 기능이므로 구현 시 minor bump. 이번 스펙 작성으로 버전을 올리거나 0.16.4 후보를 바꾸지 않습니다.

## 11. 구현 순서와 완료 정의

1. protocol과 서비스의 캐시/안내/미루기/정책 계약, foreground/activity 근거를 먼저 구현합니다. 기존 read/redeem 안전 경로를 유지하고 안내 조회와 quote를 분리합니다.
2. 서비스의 순수 판단·조회 합침·안내 persistence를 연결합니다. scheduler와 bridge에는 신선한 요약의 제한적 tie-breaker만 연결합니다.
3. desktop 공통 목록/확인 패널 및 메뉴바/트레이 사용자 진입을 연결합니다. 기존 권한/개인정보/i18n 패턴을 따릅니다.
4. omp 상태/명시 읽기 명령과 launcher의 안전한 종료 경계 안내를 연결합니다. 원본 CLI TTY 점유 중 개입하지 않습니다.
5. §9–10의 실제 사용자 여정/OS 검증·성능 측정 후 문서/변경 기록/릴리스 정책에 맞춰 별도 버전으로 배포합니다.

완료 조건: 위 구성 전체가 연결되어 사용자가 **안내 확인 → 대상 이해 → 명시 승인 → 결과 확인 → 지원되는 방식으로 업무 계속**까지 할 수 있어야 합니다. 정상·없음·미확인·미지원·취소·불명 결과에서 다음 행동이 있어야 합니다. 표시만 된 mock, 소비만 되고 결과 복구가 없는 구현, 한 OS/한 도구 검증으로 전체 완료라 하지 않습니다.

## 12. 미확인 사실과 리서치 근거

- 실계정마다 쿠폰 필드/프로그램 제공 여부, 사전 사용 허용·소진 scope, cooldown, 다른 기기 동시 소비 처리, 공급자 request-id 중복 방지는 아직 검증되지 않았습니다. §10의 실계정 게이트를 통과하기 전 지원 범위를 과장하지 않습니다.
- 공식 CLI가 초기화 뒤 같은 실행에서 자동 회복하는지는 별도 실기 증거가 없습니다. 이 문서는 자동 같은 계정 재개를 약속하지 않습니다.
- 현재 local 소비 gate는 여러 PC의 분산 잠금이 아닙니다. 실계정 요청 결과 unknown은 새 기능에서도 자동 재시도하지 않습니다.
- [Apple HIG: Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications): 동일 이벤트 반복 안내 금지, 비방해 인앱 표시, 민감정보 제외. 이번 제품은 그보다 보수적으로 OS toast 없이 동작합니다.
- [Microsoft: Notifications design basics](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-ux-guidance): 업무 흐름을 방해하지 않는 안내와 명시적 사용자 의도 존중. 앱 활성화는 사용자 동작 뒤에만 수행합니다.
- 내부 근거: [서비스](../domains/service-core.md), [데스크톱](../domains/desktop.md), [실행기](../domains/launcher.md), [omp 브릿지](../domains/omp-bridge.md), [전 생명주기 검증 계획](2026-10-21-reliability-lifecycle-verification.md).

### 문서 검증 기록

- 코드/도메인 문서 정적 조사 및 Apple/Microsoft 공식 UX 지침 확인. 기능 구현·성능 측정·실계정 소비·설치 검증은 수행하지 않았습니다.
- 독립 scout 두 건으로 서비스/화면 제약을 조사하고 소스와 대조했습니다. advisor 경로는 Codex 인증 실패·다른 공급자의 유효 검토 부재로 검토 증거로 쓰지 않았습니다. 별도 Claude read-only 검토 2회에서 지적한 캐시/quote 분리, 실제 GET·인증 비용, 기간 의미, TTY 안내, 소진 관측 freshness, requires_limit=false 분기와 탐지 공백을 반영했습니다.
- 검토 중 제안된 쿠폰 배정 기능 제거, 미루기 뒤 같은 쿠폰 재촉은 사용자 합의와 달라 채택하지 않았습니다. 실제 업무의 배정과 인공 소진을 구분하고 미루기 보존·수동 복구 안내를 명시했습니다.
- 문서 구조 검사로 시나리오 ID 중복과 로컬 문서 링크 누락을 확인합니다. 기능 시나리오 실행 상태는 계속 `NOT_RUN`이며 성능 수치는 미측정 인수 기준입니다. 구현 브랜치 생성·코드 변경·쿠폰 소비·배포는 하지 않았습니다.
