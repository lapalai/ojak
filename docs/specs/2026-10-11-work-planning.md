# 작업 계획 — 용량 런웨이 제품 기획안

## 1. 제품 정의

**Ojak 작업 계획은 현재 작업량을 계속 돌린다고 가정할 때, 보유한 여러 구독 계정이 리셋 주기를 포함해 얼마나 오래 버티는지, 처음 어디에서 막히는지, 그 공백을 무엇으로 메울 수 있는지 보여 준다.**

핵심 가치는 두 가지다.

1. **용량 런웨이:** 지금 방식 그대로 돌리면 언제까지 이어지는가.
2. **실행 가능한 공백 해소:** 공백이 생기면 기존 계정·자연 리셋·초기화권·크레딧·플랜 변경 중 무엇이 그 공백을 실제로 얼마나 줄이는가.

기본 가정은 **현재 작업량을 계속 유지**하는 것이다. 사용자는 아무 입력 없이 이 결과를 본다. 쉬라고 권하지 않고, 사용량을 늘리라고도 하지 않는다. 지출이 필요한지는 공백이 실제로 메워지는지로만 판단하며, 지출은 어떤 경우에도 사용자의 명시 확인 후에만 진행한다.

본 문서는 **제품 정책 제안**이다. 기능 구현, 실제 계정의 고갈 예측, Claude 초기화권 지원, 구독·크레딧 추가의 효과를 검증했다는 뜻이 아니다. 설치기 개선 작업과 별개이며, 이 기능의 구현·초기화권 소비·구독 구매·크레딧 사용은 아직 승인되지 않았다.

## 2. 고객·문제·경쟁 관점

### 대상 고객

Claude Code·Codex·omp 같은 코딩 에이전트를 **하루 종일, 여러 세션·여러 프로젝트로 연속 가동하는 개인 파워 유저**. 한도 때문에 작업을 멈추기 싫어 구독 계정을 둘 이상 보유하거나 보유를 검토 중이다. 이 PC에서 여러 계정·모델·플랜을 한 사용자로 운영한다(Ojak의 기존 전제).

### 해결할 일 (JTBD)

"지금 돌리는 일이 끊기지 않고 이어지는지 알고 싶고, 끊길 것 같으면 내가 가진 것으로 메울 수 있는지, 아니면 돈을 쓸 가치가 있는지 알고 싶다."

### 현재 비용 (예상치 못한 중단과 수동 관리)

- 한도 소진을 **일이 멈춘 뒤에야** 안다. 공급자 화면은 계정별로 흩어져 있고 계정·모델·5시간·주간 한도가 서로 다른 시각에 풀린다.
- 어느 계정이 막혔는지, 다른 계정이 이 작업을 이어받을 수 있는지, 언제 풀리는지를 사람이 직접 계정을 돌며 확인한다.
- 구독을 추가할지·초기화권을 쓸지·크레딧을 쓸지 **공백이 실제로 메워지는지 모른 채** 판단한다.

위 항목은 제품 가설이며, 사용자별 실제 빈도·비용은 아직 측정하지 않았다.

### 차별점

공급자 화면은 **한 계정의 한도**를 보여 준다. Ojak은 이 PC에서 여러 계정·공급자·모델의 **허용 조합**과 실제 배정(핀·제외·allowlist·reserve·lease)을 알고 있다. 그래서 "어느 계정 한 곳이 찼다"가 아니라 "내 허용 구성에서 **현재 작업 방식이 처음 흔들리는 곳**과 **전체가 막히는 구간**, **사람 손이 필요해지는 시점**"을 말할 수 있다. 이것은 다계정·모델 병목 문제에서만 의미가 있으며, 단일 계정 사용자에게는 이 제품의 가치가 작다.

### 포지셔닝

"**내 구독들로 지금 하는 일을 얼마나 오래 이어갈 수 있는가, 그리고 그 공백을 메우는 가장 효과적인 방법은 무엇인가**"를 알려 주는 용량 계획 도구. 토큰 소비 최대화 도구·절약 도구·구매 유도 도구가 아니다.

### 제품 경계

- 하지 않는다: 토큰↔구독 한도 환산, 이질적 플랜 간 퍼센트 합산, 프로젝트 완성일 예측, 한도 우회·계정 공유 권유, 실행 중 세션 강제 종료·자동 이주, 자동 구매, 인증 경로 변경.
- 알려 준다: 관측·공급자가 알린 사실, 조건부 런웨이 범위, 공백이 생기는 조건, 선택지별 공백 해소 효과와 대가.
- 사용자가 결정한다: 계속·조정·지출 여부. 시스템이 우선순위를 강제하지 않는다.

## 3. 현재 확인한 사실과 부족한 데이터

- `apps/desktop/src-tauri/src/local_usage.rs`는 이 PC의 응답 시각·도구·모델·입출력/캐시 토큰·해시 세션을 색인한다. 현재 기록에는 직접적인 계정·프로젝트 귀속이 없다. 프롬프트·이메일·인증 정보는 색인하지 않는다.
- `crates/protocol/src/lib.rs`의 `QuotaBucket`에는 `used_percent`, `resets_at`, `observed_at`, `status`가 있다. `crates/service/src/store.rs`의 계정 저장은 최신 상태 중심이며 런웨이 예측용 한도 시계열은 별도로 구축해야 한다.
- 실제 읽기 전용 색인 조회에서 10월 8일~10일 omp 응답은 각각 5,169·8,460·10,341건이었다. 활동 편차의 근거일 뿐, 한도 소비량이나 동시성·프로젝트 진척도를 뜻하지 않는다.
- **'현재 작업량'을 정의할 직접 데이터가 없다.** 현재 기록은 응답 수·세션 수이고, 실제 활성 동시 실행·lease 상태와 연결하는 계약은 아직 없다. 따라서 런웨이는 이 데이터 계약이 마련되기 전까지 계정·버킷 단위의 한도 관측과 사용자가 확인한 가정으로만 계산할 수 있다.
- Codex 공식 소스에 초기화권 목록·소비 경로가 존재한다: https://github.com/openai/codex/blob/main/codex-rs/backend-client/src/client/rate_limit_resets.rs . 실제 계정의 보유 여부, 권종별 적용 범위, 초기화 효과는 별도로 확인해야 한다. 이 기획 중 실제 소비를 수행하지 않았다.
- Claude의 초기화권 연동 경로는 미확인이다. 제공하지 않는다고 단정하지 않으며, 미검증 상태를 '없음'으로 표시하지 않는다.
- 사용자가 제공한 Claude 사용량 화면에서 계정별 소진 예상 문구, 현재 세션·주간·모델별 주간 한도, 일일 권장, 하단 '제한 초기화' 제목을 확인했다. 잘린 초기화 영역만으로 권종·개수·유효성·사용 API까지 확인한 것은 아니다. 화면의 예측은 '공급자 화면의 예측'이라는 출처를 유지하며, 기계 판독 가능한 제공 경로는 아직 미확인이다.
- 크레딧·추가 사용량·플랜별 실제 용량과 가격의 기계 판독 경로는 확인하지 않았다. 플랜 용량은 현재 계정의 단순 복제로 가정하지 않는다.

## 4. 사용자 입력

기본은 입력 없음이다. 기본 시나리오는 **현재 작업량을 쉬지 않고 유지**한다. 연속 소비를 가정한다는 뜻이며, 예측은 신뢰 가능한 유한 구간(기본 24시간, 확장 7일) 안에서만 제공한다.

필요한 시점에 선택적으로 받는다.

1. **추가 지출 없음 (선택 제약):** 켜면 크레딧·플랜 변경·구독 추가를 선택지에서 뺀다. 이 경우 남는 공백을 숨기지 않고 그대로 보여 준다. 끄는 것이 기본이며, 끈다고 지출이 허용되는 것은 아니다(§8).
2. **계속 유지가 필수인 작업 (선택):** 공백이 생겼을 때 어떤 작업이 먼저 영향받는지 보여 주는 용도. 미지정이면 모든 작업을 같은 비중의 현재 작업량으로 보며 시스템이 임의 종료하지 않는다.
3. **계획 구간 (선택):** 기본 24시간, 확장 7일이며 근거가 부족한 구간은 판단을 보류한다. 특정 마감·귀가 시각이 있으면 입력해 그 구간을 비교한다. 마감은 용량 비교용이며 코드 완성일을 예측하거나 준수를 보장하지 않는다.
4. **무인 가동 여부:** 사람의 부재·PC 절전을 자동으로 수요 0으로 해석하지 않는다. 실행기가 실제로 켜져 있고 계속 실행된다는 조건을 확인하고, 확인할 수 없으면 '실행 환경 유지 필요'를 표시한다.
5. **허용 범위:** 모델·공급자 대체, 유료 fallback, 초기화권 자동 사용, 크레딧 사용은 각각 구분하며 기본 꺼짐이다. 수동 비교는 언제든 볼 수 있다.

## 5. 화면 구성

기존 사용 현황을 **홈**으로 개편하고 화면 제목을 **연속 가동**으로 제안한다. 메뉴는 홈 / 세션 / 토큰·비용 / 연결로 두며 별도 작업 계획 메뉴는 추가하지 않는다. 상단 가동 전망 → 중단·회복 타임라인 → 필요한 경우 추천 행동 → 현재 작업·계정 상세 순서다. 계정별 잔여량과 리셋은 삭제하지 않고 판단 근거 영역으로 내린다. 이 구조는 제안이며 이번 버그 수정 릴리스의 UI 구현 범위가 아니다.

### 상단: 런웨이 요약

"현재 작업량을 그대로 유지하면 …"이라는 조건을 명시하고 다음 세 지점을 **각각 독립적으로** 보여 준다. 순서가 항상 같다고 가정하지 않으며, 한 지점이 없다고 다른 지점이 없다는 뜻이 아니다.

| 지점 | 정의 |
|---|---|
| **첫 용량 저하** | 허용된 계정·모델 구성에서 현재 병렬 처리량이나 선호 모델 구성을 처음 유지할 수 없게 되는 시점. 아직 신규 작업은 시작할 수 있다. |
| **호환 계정 전체 차단** | 프로젝트가 허용한 모든 호환 계정·모델에서 신규 작업을 시작할 수 없는 구간. 시작·종료(회복) 시점은 별도로 표시한다. |
| **무인 연속 불가 (수동 인계 필요)** | 사람 개입 없이는 이어갈 수 없게 되는 첫 시점. 예: 실행 중 세션이 막힌 계정에 묶여 새 세션·이어가기를 사용자가 해야 함, 로그인·인증 문제, 자동 사용이 꺼진 초기화권 수동 사용, 확인이 필요한 지출. Ojak은 대화를 자동 이주하지 않으므로 이 지점이 별도로 필요하다. |

각 지점에는 `해당 구간 내 없음 / 시점 범위 / 이미 발생 / 판단 자료 부족`을 쓴다. 근거 없는 확률 숫자는 쓰지 않으며, 마지막 관측 시각·적용 가정·신뢰 근거를 함께 표시한다.

런웨이는 **리셋 주기를 포함해** 계산한다. 공급자가 알린 5시간·주간·모델별 리셋을 반영해 회복 후 다시 같은 지점에 도달하는지 본다. 결과는 다음 중 하나다.

- 관측 범위 X까지 유지 (X 이후는 판단 보류)
- 리셋 때마다 같은 공백이 반복됨 (어느 버킷·계정·모델인지 포함)
- 공백 해소 후에도 다음 주기에서 재발

'유지 가능'은 관측 범위와 현재 작업량 유지 조건 안에서의 조건부 표현이며, 영구 고갈 날짜나 보장이 아니다. 전체 사용률 한 숫자로 뭉개지 않는다.

### 중단·회복 타임라인

사용자가 고른 구간을 기본으로, 없으면 다음 24시간을 표시하고 주간 한도 영향은 다음 7일 보기로 확장한다. 24시간·7일은 화면 범위이지 그 기간을 신뢰성 있게 예측한다는 보장이 아니다.

- 현재 병렬 처리량을 유지하기 어려운 구간
- 요청한 모델로 신규 작업을 시작할 수 없는 구간
- 호환 계정 전체 차단 구간
- 공급자가 알린 자연 리셋 예정과 실제 회복 확인

공급자가 표시한 계정별 소진 예측을 신뢰 가능한 경로로 수집할 수 있으면 '공급자 예측'으로 따로 표시한다. Ojak의 다계정 런웨이와 출처·범위를 섞지 않는다. '일일 권장' 같은 소비 속도 안내는 강제 한도와 별도이며, 사용을 늘리도록 유도하지 않는다. 가까운 세션 리셋이 와도 주간·공통 한도가 막혀 있으면 회복으로 계산하지 않고, 공통 한도와 모델별 한도의 잔여량을 더하지 않는다.

### 공백 해소 비교

공백(위 세 지점 중 하나라도 계획 구간 안에 있을 때)이 있으면 해소 선택지를 같은 구간에서 비교한다.

- 기존 허용 계정·모델로 라우팅(제외·핀 설정은 존중하며, 되살리는 것은 사용자의 결정으로만 제안)
- 자연 리셋을 기다림 (공백이 계속되는 시간 그대로 표시)
- 초기화권
- 크레딧·추가 사용량
- 플랜 변경 또는 구독 추가

각 선택지에 표시한다.

- **어느 지점이 얼마나 이동하는가:** 첫 용량 저하·전체 차단·수동 인계 필요 시점의 변화와 남는 공백
- 효과가 나타나는 시점, 전제, 불확실성
- 소모되는 초기화권 수, 확인된 실제 비용 또는 사용자 입력 비용
- 가역 여부, 확인이 필요한 행동인지

기존 계정·자연 리셋·초기화권을 먼저 검토하고 크레딧·플랜은 그 다음에 검토한다. 이는 **표시·검토 순서일 뿐 강제 우선순위가 아니다.** 앞선 선택지로 공백이 메워지지 않으면 뒤 선택지가 실제 공백을 줄이는 경우에 한해 추천 후보가 되며, 공백을 줄이지 못하는 지출은 추천에서 제외한다. 추천 하나와 유효한 대안 둘을 먼저 보여주고 전체 비교는 펼친다. 추가 구독에는 상위 플랜 변경도 포함하며 한도 우회·계정 공유를 권하지 않고, 공급자 약관상 허용되는 사용인지 별도 확인이 필요하다.

작업량을 줄이는 가정은 사용자가 요청한 what-if로만 제공한다. 기본 추천으로 '쉬어라·줄여라'를 말하지 않는다.

## 6. 예측 계산 정책

### 6.1 관측과 귀속

- 동일 계정·workspace·모델·한도 종류의 신선한 스냅샷을 연속 관측한다. 계정별 정책과 초기화권 상태도 시간과 함께 기록한다.
- 실제 관측된 한도 감소량으로 소모율을 추정한다. 단순 토큰 수·API 환산액을 구독 한도로 환산하지 않는다. 토큰 기록은 작업량 변화·모델 변화의 보조 신호로만 쓴다.
- 리셋·초기화권 사용·계정 식별 변경·플랜 변경 시 이전 구간과 분리한다. 감소/증가를 무조건 소비나 회복으로 해석하지 않는다.
- 프로젝트별 영향 설명에는 세션↔프로젝트↔계정 연결이 필요하다. 검증된 연결이 없는 기록은 '미분류'로 두고 특정 프로젝트를 원인으로 지목하지 않는다.
- 응답 수와 세션 수는 동시성이 아니다. 실제 활성 실행 관측과 lease 상태를 구분해서 사용하며, 불확실 lease는 여유 슬롯으로 세지 않는다.
- 같은 실제 계정의 여러 프로필, 공유 workspace 한도, 공통/모델별 중첩 제한을 중복 용량으로 계산하지 않는다.
- 세션 귀속은 필요조건일 뿐 한도 소비 분해의 충분조건이 아니다. 여러 프로젝트가 같은 계정/버킷을 동시에 쓰면 감소량만으로 각 기여를 식별할 수 없다. 단독 관측 구간 등으로 검증된 기여만 프로젝트별 효과에 사용하고 나머지는 공동 소비·미귀속으로 남긴다. 토큰 비중으로 나눈 값을 실측으로 표시하지 않는다.

필수 데이터 계약은 (a) 소스 관측 시각과 수집 시각이 구분된 계정·버킷 스냅샷, (b) 검증된 실행/세션·프로젝트·계정 매핑과 매핑 신뢰도, (c) 실제 활성 실행·무인 가동 여부, (d) 관측/가정/미귀속을 구분하는 예측 응답, (e) 초기화권 미확정 실행 상태, (f) 수동 인계가 필요한 상태(세션이 묶인 계정 차단·인증 문제·사용자 확인 대기)다. 서비스·launcher/observer·desktop 경계에서 이 계약이 전달돼야 하며, 정확한 RPC/DB 스키마는 구현 설계에서 정한다. 현재 프로토콜에 이미 존재한다고 가정하지 않는다.

### 6.2 호환 계정과 실제 병목

프로젝트의 허용 모델·계정·수동 제외·핀·동시 실행·안전 여유량을 그대로 적용한다. 다른 공급자/모델로 대체하는 시나리오는 사용자가 허용한 경우에만 계산한다. 같은 모델이라도 플랜별 1%를 동일한 절대 용량으로 가정하지 않으며, 이질적인 플랜·버킷의 퍼센트를 합산하지 않는다. 용량은 계정·버킷·모델별로 따로 유지하고, 배정을 먼저 막는 조건을 병목으로 삼는다.

현재 세션은 배정 계정에 묶인 상태로 계산한다. 다른 계정의 여유는 새 세션이나 사용자가 명시적으로 이어가기로 한 경로에만 반영한다. Ojak이 대화를 자동 이주·중단할 수 있다고 가정하지 않는다.

### 6.3 시간에 따른 시뮬레이션

현재 작업량(기본)과 최근 평소 작업량을 계정·모델별로 시뮬레이션한다. 5시간·주간·모델별 제한은 독립적으로 점검한다. 미래 리셋은 공급자 관측/검증된 의미를 사용하며, 알 수 없는 반복 주기를 만들어 내지 않는다.

권장 학습 창은 최근 작업 구간(현재 부하)과 최근 여러 활성일(평소 부하)을 함께 쓰는 것이다. 구체 가중치·관측 주기·임계값은 별도 검증 대상이며 이 문서의 확정 실측값이 아니다. 작업 구성과 모델이 달라지면 과거 평균을 그대로 적용하지 않는다.

초기화권·크레딧·추가 계정·플랜 변경의 가상 결과는 '해당 조건이 유지된다면'의 예상이다. 실제 절약 시간이나 실제 수익으로 표현하지 않는다. 확인되지 않은 신규 플랜의 용량은 현재 계정의 단순 복제로 확정하지 않고 사용자가 볼 수 있는 가정으로 둔다.

무인 시나리오는 실행기가 실제로 켜져 있고 작업을 계속 실행한다는 조건부 계산이다. 로컬 PC 절전·덮개 닫기·전원 상태와 원격 실행 여부를 확인할 수 없으면 '실행 환경 유지 필요'를 표시한다. Ojak이 절전을 자동 해제하거나 프로세스를 임의 제어하지 않는다. 환경이 중단되면 예측을 재계산하고 이를 한도 부족이나 수요 감소로 오인하지 않는다.

### 6.4 신뢰 수준별 허용 출력

- 현재값만 있음: 현재 상태·리셋 예정·초기화권 사실을 표시. 런웨이 범위는 제공하지 않는다.
- 짧은 신선한 연속 관측: 현재 작업량 유지 조건의 단기 범위만 제공. 주간/월간 결론은 보류한다.
- 여러 작업일·리셋 주기 관측: 리셋 주기를 포함한 런웨이 범위와 반복 공백 분석을 제공한다.
- 오래된 관측·PC 절전·다른 기기 사용 가능성·인덱스 미완료·설명 안 되는 한도 변화: 관련 예측만 신뢰도를 낮추거나 보류하고 재관측한다.

한도 때문에 강제로 멈췄던 시간은 원래 수요가 없던 시간으로 학습하지 않는다. 공급자 총사용량과 이 PC 기록 차이는 미귀속 소비로 남기며 특정 다른 기기 사용이라고 단정하지 않는다. 예측 신뢰도와 초기화권 사용 가능 여부는 서로 다른 판단이다.

보류는 판단별로 적용한다. 프로젝트 귀속이 부족해도 검증된 계정군의 현재 한도·리셋 정보는 제공하고, 장기 구매 추천 근거가 부족해도 사용자 요청 가정 비교는 제공한다. 한 가지 미확인 값 때문에 전체 화면을 '학습 중'으로 잠그지 않는다.

## 7. 추천 정책

공통 순서: **세 지점 계산 → 공백 원인 분류 → 사용자 제약을 지키는 선택지 생성 → 같은 구간에서 공백 해소 효과 비교 → 추천 → 실행 직전 재확인**.

### 공백 없음

허용된 계정으로 계획 구간(기본: 관측 범위)을 감당하면 '조치 필요 없음'과 관측 범위를 표시한다. 사용률이 높다는 이유만으로 경고하지 않는다. 실행 중 세션의 개별 위험은 별도 표시한다.

### 추천 기준

- 후보는 위 세 지점 중 하나 이상을 **관측 근거로 이동시키는** 선택지뿐이다. 이동을 근거로 설명할 수 없으면 추천하지 않는다.
- 같은 공백을 메우는 선택지가 여럿이면 비가역·유료 정도가 낮고 불확실성이 작은 쪽을 먼저 제시한다. 이 때문에 보통 기존 계정·자연 리셋이 앞에 오지만, 그것이 공백을 메우지 못하면 뒤 선택지가 앞선다. 지출을 위한 지출, 사용 유도를 위한 소비를 추천하지 않는다.
- '추가 지출 없음' 제약이 켜져 있으면 유료 선택지를 후보에서 빼고 남는 공백과 그 시점을 명시한다. 제약이 꺼져 있어도 유료 선택지는 효과가 확인되는 경우에만 제시한다.
- 효과가 모델별 제한·로그인 문제·서비스 장애 등 다른 원인에서 나온 공백에는 초기화권·계정 구매를 추천하지 않는다.

### 기존 계정·자연 리셋

허용된 다른 계정에 신규 작업을 보낼 수 있으면 먼저 표시한다. 그러나 이미 막힌 계정에 묶인 실행 중 세션은 그대로 막혀 있음을 별도로 표시한다. 자연 리셋을 기다리는 선택지는 그 시간 동안의 공백을 숨기지 않는다. 한 번의 가장 이른 리셋만으로 '전체 재개 가능'이라고 하지 않고 관련 버킷을 모두 확인한다.

### 초기화권

막힌 한도에 적용되는 유효한 초기화권이 공백을 유의미하게 줄일 때 추천한다. 자연 리셋이 가깝다는 이유만으로 금지하지 않으며 사용자의 허용 대기·계획 구간을 고려한다. 만료 임박만으로 소모를 재촉하지 않는다.

### 크레딧·구독 검토

- 자동 추천: 실제 필요한 구간의 공백이 서로 다른 리셋 주기에서 반복되고, 구성 변경이 그 공백을 줄인다는 근거를 설명할 수 있을 때 제시한다.
- 사용자 요청 비교: 이력이 부족해도 가정을 표시한 비교는 허용한다. 단발성 긴급 구간에서도 선택지를 숨기지 않는다.
- 플랜 용량·가격·약관 조건이 불명확하면 확정적인 구매 추천은 하지 않는다.
- 월 구독료·크레딧 비용과 남는 공백을 나란히 표시한다. 사용자 시간의 금전 가치를 임의 산정하지 않는다.
- 효과 없는 조치는 추천에서 제외한다.

## 8. 지출·초기화권 실행 정책

### 지출

- 구독 구매·플랜 변경·크레딧 사용·유료 fallback은 자동으로 실행하지 않는다. 실행 전에 **행동·금액(확인된 값 또는 알 수 없음)·기대 효과(가정 포함)·가역 여부**를 보여 주고 그 행동에 대한 명시적 확인을 받는다. 이전 확인이나 '추가 지출 없음' 해제는 새로운 지출의 허가가 아니다.
- 유료 크레딧·추가 사용량은 초기화권과 다른 기능이며 기존 opt-in을 유지한다.

### 초기화권

- 기본: 표시·추천만. 자동 사용은 계정별 별도 opt-in이며 대상 작업·사용 상한·허용 상황을 확인한 뒤 활성화한다. 수동 제외 계정을 되살리거나 과금 fallback을 켜는 권한이 아니다.
- 실행 조건: 최신 실제 소진, 계속할 작업 존재, 적용 범위 확인, 다른 허용 용량/대기 대안 평가, 유효한 초기화권, 사용 상한 미도달, 미해결 이전 요청 없음.
- 회당 1장. 필요한 한도를 회복하는 권종 중 만료가 빠른 것을 우선하고 공급자가 제한한 사용 조건을 준수한다.
- 사용 요청 전 계정별 단일 실행 잠금과 `redeem_request_id`를 로컬에 영속화한다. 응답 유실 시 새 요청 ID/다른 초기화권으로 재소모하지 않는다. 공급자가 보장한 멱등 의미·기간을 확인한 경우에만 같은 요청을 안전하게 재확인한다.
- 공급자별 적용 범위·멱등 의미·결과 확인 경로의 검증이 자동 사용 활성화의 출시 조건이다. 미검증 공급자/권종은 자동 사용을 제공하지 않고 공식 수동 경로와 상태 재조회를 안내한다. 미확정 결과가 해소되지 않으면 해당 계정의 자동 사용만 보류하고 나머지 계정의 계획 기능은 유지한다.
- '사용 성공 응답'과 '실제 한도 회복 확인'을 구분한다. 이미 사용됨·사용 대상 없음·초기화할 필요 없음·권한 오류를 모두 성공으로 처리하지 않는다.
- 사용 효과가 확인되지 않았거나 결과가 불명확하면 자동 소모를 보류한다. 시간 경과만으로 해소하지 않고 새 조회로 확인한다.
- Claude는 연동 경로가 검증될 때까지 '연동 미확인'. 수동으로 외부에서 초기화한 후 한도 회복을 관측할 수는 있지만 Ojak의 소비 성공으로 기록하지 않는다.

## 9. 알림·사용자 제어

같은 조건에서 추천이 흔들리지 않도록 의미 있는 변화와 관측 지속성을 기준으로 갱신한다. 실제 차단·실제 회복은 즉시 반영한다. 신선도 만료도 재평가 이벤트이며 기존 추천을 그대로 두지 않는다.

알림은 세 지점 중 하나의 시점이 계획 구간으로 들어옴(특히 수동 인계 필요), 선택한 재개 조건 충족, 초기화권 자동 사용 결과/불확실 상태에 한정한다. 단순 퍼센트 변화마다 알리지 않는다. '이번 추천 무시'는 같은 근거의 반복 알림을 억제하지만 새로운 중대한 상황은 설명과 함께 알린다. 취침 모드에서는 사용자가 정한 알림 범위를 지킨다.

추천 변경에는 변경 이유를 한 줄로 제공한다. 수동 제외·핀·allowlist·reserve·불확실 lease 보호는 추천 설정으로 우회되지 않는다. 사용자가 정책을 바꾸면 관련 예측은 다시 계산한다.

## 11. 제품 성과와 개인정보

우선 지표는 사용자가 현재 작업량을 유지하려던 구간에서의 **예상치 못한 중단 횟수**, **사전 경고 없이 발생한 수동 인계·차단 횟수와 경고 선행 시간**, **예측 범위의 실제 적중/빗나감**, 추천의 잦은 번복, 불필요한 초기화권 소모, 수동으로 계정을 확인해야 했던 횟수(선택 보고), 사용자의 선택적 후회/도움 피드백이다. 구매 전환율·토큰 소모량을 목표로 삼지 않는다.

- 예측 평가는 사후 관측과의 비교다. 예측한 첫 용량 저하 범위와 실제 관측 시점이 맞았는지 센다.
- 관측된 대기·차단 시간과 가상 시나리오의 절약 시간을 분리한다. 선택하지 않은 시나리오의 결과는 반사실 추정이지 실제 성과가 아니다. 추천 전후 차이를 인과 효과라고 단정하지 않고, '이 제품 덕분에 몇 시간 더 일했다' 같은 주장을 하지 않는다.
- 위 지표는 구현 후 로컬 관측으로 정의하며, 현재 기준선은 측정하지 않았다.

시계열·프로젝트 매핑·운영 계획·초기화권 실행 상태는 로컬 저장한다. 프롬프트·인증 토큰·이메일은 수집하지 않으며 프로젝트 경로와 상세 부재 일정은 진단 내보내기에서 기본 제외한다. 중복 사용 방지에 필요한 내부 식별자는 보호된 로컬 상태에 저장하되 일반 로그·화면에 노출하지 않는다. 수집·보존 기간과 삭제 기능은 구현 시 명시한다. 삭제 후 근거 없는 과거 예측을 유지하지 않으며, 미확정 소모 상태를 일반 이력 삭제로 없애 재소모를 허용해서는 안 된다.

## 12. 구현 완료 기준과 별도 승인 범위

이 기획의 완료는 상태 카드만 있는 화면이 아니다. 관측·귀속 → 리셋 포함 런웨이(세 지점) → 동일 구간 공백 해소 비교 → 설명 가능한 추천 → 선택한 조치의 재검증까지 이어져야 한다. 플랫폼별 실제 관측과 한도 회복·실패 경로를 검증해야 한다.

순서는 데이터/회귀 검증, 읽기 전용 런웨이·비교, 실제 초기화권 조회/수동 사용 검증, 명시 opt-in 자동 사용으로 둔다. 이는 데이터 및 비가역 실행의 선행조건 순서이며, 사용자가 승인한 범위를 임의로 줄여 완료라고 부르지 않는다.

구현 전 추가로 확정할 사항: '현재 작업량'의 측정 방식(활성 실행·lease 연계), 공급자별 초기화권 scope/멱등 계약, 모델·계정·프로젝트 귀속 수단과 누락 처리, 크레딧·플랜 용량·가격의 판독 경로, 시계열 보존 기간, 자동 사용 상한의 기본값, 예측 신뢰도 보정 기준, 실제 플랜 정보의 최신성. 확인 전까지 추정 사실로 고정하지 않는다.
