# 0.9.2 Windows 설치·실행 검증

## 확인된 원인과 reference

사용자 사진은 트레이가 아니라 `Ojak Setup: UPDATE_RECOVERY_REQUIRED (stage=prepare, exit=1)`였다. 0.9.1 `prepare`는 receipt 또는 backup이 있으면 중단하고, NSIS 종료 복구는 이번 prepare가 성공했을 때만 실행했다. 따라서 안내대로 다시 실행해도 이전 트랜잭션을 처리하지 못했다. receipt 없는 backup의 `recover`는 성공을 반환하면서 디렉터리를 남기는 결함도 개발 Windows에서 재현했다.

- [NSIS .onInstFailed](https://nsis.sourceforge.io/Docs/Chapter4.html#oninstfailed) / [.onGUIEnd](https://nsis.sourceforge.io/Docs/Chapter4.html#onguiend): 강제 종료의 복구를 보장하지 않고, 무인 설치에는 GUI callback이 실행되지 않는다.
- [NSIS 단일 인스턴스](https://nsis.sourceforge.io/Allow_only_one_installer_instance) / [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew): share=0과 delete-on-close로 설치·제거를 직렬화하고 비정상 종료 뒤 OS가 잠금을 회수한다.
- 실제 Tauri CLI 2.12.1 생성 template에서 이전 uninstaller 호출은 PREINSTALL보다 앞이다. 잠금을 `.onInit` 대신 PREINSTALL/PREUNINSTALL의 첫 변경 전에 잡아 parent/child 교착을 피한다.
- helper는 binary의 공통 installer dispatch에서 독점 파일 잠금을 유지한다. 부모가 종료된 뒤 살아 있는 helper도 보호하며, 서비스 자식에 핸들을 상속하지 않는다. backup cleanup은 operation lock 파일을 삭제하지 않는다.

## 실행 검증 (서명 후보 생성 전)

- Mac: Rust 263개, Tauri 68개(기존 1 ignored), desktop 87개, omp 11개와 typecheck 통과.
- Windows: 새 target·node_modules 디렉터리에서 Rust 272개, Tauri 63개(기존 1 ignored), desktop·omp·typecheck 명령 통과. 과거 빌드의 junction은 unlink하고 새 의존성을 설치했다. Tauri test에는 실제 빌드한 sidecar를 먼저 준비했다.
- Windows 실제 launcher와 격리 `AAM_HOME`으로 아래 10개 케이스를 일반 사용자 권한에서 실행했다. 운영 앱·서비스·계정·레지스트리를 변경하지 않았다.

| 케이스 | 0.9.1 | 수정된 0.9.2 |
|---|---|---|
| prepare 후 정상 recover | 원본·shim 복원 | 원본·shim 복원 |
| 중단 뒤 prepare 재호출 | UPDATE_RECOVERY_REQUIRED | 내부 CLI는 계속 안전하게 거절; 실제 NSIS가 recover 후 재개 |
| receipt 없는 동일 backup | recover가 성공했지만 다음 설치는 막힘 | 현재 해시 검증 후 정리, 다음 prepare 가능 |
| receipt 없는 빈 backup | 같은 막힘 | 정리 후 다음 prepare 가능 |
| backup 없이 남은 legacy receipt | 복구 실패 | 현재 원본 해시가 증명될 때만 정리 |
| 실행 파일 backup 변조 | 거절·보존 | 거절·보존 |
| shim backup 변조 | 거절·보존 | 거절·보존 |
| 다른 directory의 receipt | 거절·보존 | 거절·보존 |
| 다른 owner의 receipt | 거절·보존 | 거절·보존 |
| 파일을 사용 중인 launcher | 거절·새 기록 없음 | 거절·새 기록 없음 |

실제 NSIS hooks와 새 native helper로 만든 격리 설치기도 실행했다:

- 중단된 prepare → `UPDATE_RECOVERY_REQUIRED` → recover 0 → prepare 0 → finish 0. 설치된 두 파일의 SHA-256이 준비한 payload와 같고 receipt/backup이 정리됨.
- 불완전 payload → `UPDATE_FILE_MISMATCH`, exit 1 → recover 0. 기존 launcher/service 두 파일 모두 원래 해시로 복원됨.
- 다른 설치 잠금 점유 → `INSTALLER_ALREADY_RUNNING`, exit 1. 앱 바이트와 receipt/backup 상태를 변경하지 않음.
- 실제 `%TEMP%\Ojak-installer.log`의 단계·종료값·코드를 회수했다. 계정·이메일·토큰·프롬프트는 기록하지 않았다.

정적 독립 리뷰에서 복구 무결성과 NSIS lifecycle을 재검토했다. 부모만 종료돼 helper가 살아 있는 경합 지적은 공통 dispatch의 helper 수명 잠금으로 보완했고, 소비자 수준 Windows 회귀와 실제 독점 잠금 거절을 확인했다.

부모 종료 추가 스트레스 케이스에서는 두 512 MiB 원본과 debug helper를 사용했다. 부모 종료 뒤 helper가 살아 있는 동안 두 번째 설치가 차단됨을 확인했지만, 처음 설정한 60초 대기 안에는 helper가 끝나지 않았다. helper 종료를 확인한 뒤 공개 0.9.2 release helper로 격리 복구를 실행해 exit 0과 두 원본의 SHA-256 복원을 확인했다. 큰 fixture는 정리했다. 이 결과를 debug NSIS의 세 번째 전체 설치 성공으로 표현하지 않는다.

## 이전 공개 GUI의 실제 앱 안 업데이트

0.9.1 서명 산출물에서 격리한 이전 GUI의 설정 화면을 사용했다. 서비스는 위에서 검증한 0.9.2를 유지했으며, 전체 서비스 다운그레이드 후 업데이트를 시험한 것은 아니다.

- Windows: 일반 사용자 0.9.1 GUI → 공개 0.9.2 offer → `설치하고 다시 시작` → 다운로드·서명 검증·실제 NSIS prepare/finish exit 0 → 설치 경로의 새 0.9.2 GUI 재시작. GUI SHA-256은 재설치 후보와 같고, 서비스 0.9.2·ready true·mismatch false·계정 9개를 확인했다.
- Mac: 정상 `open`으로 실행한 0.9.1 GUI → 공개 offer → 관리 세션 2개와 최근 omp 세션 4개 재시작 경고 → `지금 업데이트` → 격리 bundle과 재시작 GUI 0.9.2. 실행 서비스 0.9.2·ready true·mismatch false, 계정 22개와 기존 관리 세션 2개·ACTIVE 상태를 확인했다. 당시 평면 `processId` 필드를 비교한 기록은 실제 PID 연속성 증거로 사용하지 않는다. 직접 binary를 실행한 최초 테스트 GUI에서는 UPDATE_FAILED가 표시됐으며, 해당 테스트 GUI만 종료한 뒤 정상 bundle 실행으로 위 경로를 완료했다. 최초 실패의 원인을 제품 결함이나 특정 네트워크 원인으로 단정하지 않는다.
- 임시 Mac GUI만 종료하고 실제 설치 경로의 앱을 다시 열었다. Windows 검증 Task와 격리 스크립트·fixture는 정리하되, 비밀 없는 설치 단계 로그와 검증 결과는 보존한다.

실제 Windows 설치 로그의 정상 완료는 아래와 같다. 안전 차단·중단 복구 로그도 함께 회수했으며 오류를 숨기거나 같은 버전의 파일을 바꿔 재배포하지 않았다.

```text
Ojak: stage=prepare exit=0 code=OK
Ojak: stage=finish exit=0 code=OK
```

캡처의 Administrator PC는 등록된 원격 환경과 일치하지 않아 해당 PC의 원본 로그는 직접 회수하지 못했다. 사용자가 접속 가능한 개발 Windows에서 알아서 테스트하라고 승인해 위 재현·수정 검증을 진행했다. 개발 환경의 성공을 그 PC의 원격 복구 완료로 간주하지 않는다.

## 실제 Windows의 CLI·omp 및 사용 중 앱 재실행

추가 검증은 2026-10-13에 접속 가능한 Samsung 960XFH의 Windows 11 Home x64, `agus2` Interactive/Limited 사용자에서 했다. VM이나 모의 응답이 아니다. Ojak 앱·launcher·서비스는 공개 0.9.2를 유지했고, 설치 GUI SHA-256은 위 서명 후보와 동일했다.

### 발견한 Claude CLI 호환 문제와 조치

실제 관리 Claude 실행은 처음에 exit 1, `NO_ELIGIBLE_ACCOUNT`, 응답 없음으로 실패했다. 공식 CLI 2.1.268의 동일 `/usage` probe는 약 3.6초 뒤 exit 0과 모델 호출 0회를 반환했지만, Ojak이 검증하는 `usage_report`·`local_command_run` 구조가 없었다. 따라서 `QUOTA_UNKNOWN`이었으며, 단순 실행 성공을 유효한 한도로 취급하지 않았다.

공식 [업데이트 안내](https://code.claude.com/docs/en/setup#update-manually)의 `claude update`를 실행해 2.1.268 → 2.1.296으로 업데이트했다(exit 0, 약 11.3초). 원본 진입 경로와 native profile identity는 보존됐다. 한도를 다시 조회한 뒤 두 Claude 계정의 구조화된 한도를 얻었고, 실제 배정 가능한 계정은 **1개**였다. 다른 계정은 주간 한도 소진 상태로 계속 제외됐다. 아래 실제 응답·이어가기 검증은 사용 가능한 계정으로 통과했다. 2.1.268과 2.1.296을 직접 비교한 결과이지, 정확한 최소 호환 버전을 확정한 것은 아니다.

인증·한도 검사를 우회하거나 credential·DB를 수정하지 않았다. 이번 조치는 외부 공식 Claude CLI 업데이트이며 Ojak 실행 산출물 변경이 아니므로, 새 Ojak 버전이나 대체 0.9.2 파일을 배포하지 않았다.

GUI 재실행 방법은 설치 경로를 확인한 own GUI에 `WM_QUIT`을 보낸 뒤 같은 앱을 실행하는 방식이었다. Windows 전체 재부팅이나 keyboard Ctrl+C 테스트로 표현하지 않는다. Codex fresh GUI 재실행은 stdin을 기다리는 ACTIVE 상태, Claude는 첫 대화 입력 뒤 ACTIVE 상태에서 했으며, 동시 검증의 omp는 실제 모델/도구 요청 진행 중이었다.

### 로그·검증 장치의 실패 구분

비밀 없는 단계 로그와 JSON 증거는 Windows의 `C:\Users\agus2\ojak-0.9.1-release` 및 Mac 검증 산출물의 `candidate092/windows-runtime-20261013`에 보존했다. 대표 파일은 `windows-runtime-092-cases.jsonl`, `windows-{omp,claude,codex,combined}-lifecycle-{cases.jsonl,proof.json}`, `windows-native-cases.jsonl`, `claude-usage-shape-proof.json`, `claude-official-update-proof.json`이다. 원시 모델 응답·프롬프트·이메일·토큰은 로그에 넣지 않았다.

테스트 장치 자체의 실패는 제품 실패와 분리했다. 최초 service install을 임시 작업 경로에서 호출해 daemon의 cwd가 fixture 삭제를 막은 문제는 안정된 설치 경로에서 지원 명령으로 재설치한 뒤 삭제 성공을 확인했다. PowerShell 5.1 단일 객체 `.Count` 오판과 mapping 없는 Codex에 SESSION_BUSY만 기대한 잘못된 전제도 장치에서 수정했다. 이전 실패 기록을 보존하고 수정한 시나리오를 다시 실제 실행했다. 최종 네 lifecycle proof는 모두 ok true, fail/blocked 0이었다. 임시 스크립트·fixture·검증용 scheduled task는 제거하고 정상 GUI·서비스는 유지한다.

실기기 범위는 위 Windows 한 대와 단일 화면 200% 배율이다. 혼합 DPI 다중 모니터, 사진의 Administrator PC, Windows 전체 재부팅, keyboard Ctrl+C, 실제 외부 계정의 강제 로그인 만료나 한도 고갈은 시험하지 않았다. 위 범위를 모든 가능한 OS·인증·네트워크 시나리오의 통과로 확대하지 않는다.
