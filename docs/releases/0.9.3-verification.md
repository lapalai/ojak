# 0.9.3 설치 복구 검증 기록

## 대상과 원인

- 제보 화면: Windows 설치기의 `UNMANAGED_SERVICE (stage=recover, exit=1)`.
- 기존 0.9.2는 서비스 등록 기록이 없을 때도 `resume`에서 먼저 daemon을 시작했다. 이후 소유권 검사에 실패해 무기록 서비스가 남고, 다음 복구도 같은 오류로 막혔다.
- 별도 실패 경로: 기존 `finish`는 새 서비스 시작 전에 교체 파일의 증거를 영수증에 저장하지 않았다. 원본 백업은 0.9.1인데 떠 있는 서비스는 0.9.2인 상태도 실제 실행해 재현했다.
- 확인 가능한 Windows 대상은 Samsung `960XFH`, Windows 11 Home `10.0.26200`, 일반 사용자 권한이다. 제보 사진의 `Administrator` PC는 연결되지 않아 그 PC에 직접 반영했다고 주장하지 않는다.

## 적용한 안전 경계

- 소유권을 검증하기 전에 서비스를 시작하지 않는다. 새 영수증에는 등록 snapshot, 원본 해시, 교체 payload 해시를 따로 보존한다.
- 구 영수증의 무기록 서비스는 같은 SID·설치 경로·검증한 원본 백업·서비스 파일 hash·실제 pipe peer와 고정 프로세스 핸들·새 lease 안전 승인을 모두 확인한 경우에만 종료한다. 일반 `service stop`은 무기록 서비스를 계속 거절한다.
- 등록 기록을 임의로 만들지 않는 구 복구에서도 DB의 배정 차단을 완료한다. 실제 서비스의 수명 잠금을 독점하고, pipe 부재·소유 DB·지원 schema·점유/불확실 lease 부재를 확인한다. 계정·인증·lease 행은 변경하지 않는다.
- DB 취소 후 영수증 저장 전 중단되어도 재시도할 수 있다. 원본으로 rollback한 뒤 정리가 중단됐으면 원본 세대의 해시로 이어서 검증한다.
- 근거: [QueryFullProcessImageNameW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew), [GetNamedPipeServerProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid), [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex), [NSIS 실패 콜백](https://nsis.sourceforge.io/Docs/Chapter4.html#oninstfailed).

## 실제 Windows 복구 실행

격리한 `AAM_HOME`에 실제 이전 릴리스의 launcher·daemon을 실행했다. RPC·SQLite를 실제로 확인했으며 model 응답 mock이나 가짜 서비스로 성공을 대신하지 않았다. 아래 실행은 설치된 사용자 계정 데이터나 HKCU 자동 실행 등록을 변경하지 않았다.

| 시나리오 | 결과 |
|---|---|
| 구 prepare 후 등록 기록 소실, recover 두 번 | 기존 0.9.2에서 `UNMANAGED_SERVICE` 반복 재현; 수정본은 원본 복구·재시도 성공 |
| 같은 상황, 실제 8.3 짧은 경로 | 복구·재시도 성공 |
| 같은 AAM_HOME을 쓰는 다른 설치 경로의 daemon | 거절, 외부 daemon·파일 보존 |
| 다른 owner의 서비스 등록 기록 | 거절, 백업·상태 보존 |
| 다른 설치 경로를 가리키는 등록 기록 | 거절, 백업·상태 보존 |
| 등록 기록이 있는 상태에서 실행 파일 백업 변조 | 거절, 현재 파일·백업 보존 |
| 등록 기록이 없는 상태에서 실행 파일 백업 변조 | 거절, 현재 파일·백업 보존 |
| 등록 기록이 없는 상태에서 shim 상태 백업 변조 | 거절, 현재 파일·백업 보존 |
| 정상 등록 서비스의 일반 복구 | 서비스 응답·배정 재개·복구 기록 정리 성공 |
| 0.9.1 원본 백업 + 구 finish가 남긴 실제 0.9.2 무기록 daemon | 구 finish의 실패 재현 후 수정본으로 종료·원본 복구·배정 차단 해제 성공 |
| 새 영수증의 소유 snapshot은 있으나 등록 기록·저장 permit 소실 | snapshot 복구·같은 peer의 새 안전 승인·배정 재개 성공 |
| 새 finish가 소유권 검사에서 실패 | daemon 시작 전 교체 증거 보존; 원본 세대로 복구 성공 |

첫 9개 및 추가 3개 실제 실행에서 실패 check 0, 기존 자동 실행 등록·격리 환경 밖 서비스 불변, 격리 서비스 잔여 0을 확인했다. 무기록 구 복구는 DB의 `uninstallPermit`가 실제로 해제되었는지 별도로 읽어 확인했다.

처음 실패 재현에서 이미 남아 있던 별도의 실제 무기록 daemon도 수정본으로 복구했다. 종료값 0/`OK`, 원래 PID 종료, 원본 두 파일 해시 복원, 등록 기록을 새로 만들지 않음, 영수증·백업 정리를 관측했다. 이 최소 fixture의 배정 차단은 시작 전부터 해제 상태였다. 최초 harness가 차단 상태를 가정해 `ok:false`로 기록한 원본과, 측정값에 대한 정정 기록을 함께 보존했다. 차단 해제 전이를 증명하는 별도의 9-case 실행과 혼동하지 않는다.

추가 payload harness도 처음에는 복구 전용 변조 integration을 finish에 전달했고, 이후에는 원래 설치에 있어야 하는 bin 디렉터리가 빠져 실패했다. 원본 실패 로그를 보존하고 유효한 설치 fixture로 수정한 뒤 위 3개 경로를 실제 실행했다. 제품 오류를 무시하거나 성공 기준을 낮춘 결과가 아니다.

## 소스 검증

| 항목 | macOS | Windows |
|---|---|---|
| 기본 Rust suite | 263 통과 | 278 통과 |
| typecheck | 통과 | 통과 |
| desktop suite | 87 통과 | 87 통과 |
| omp 확장 suite | 11 통과 | 11 통과 |

Windows 회귀 테스트에는 승인 불일치의 배정 차단 유지, 취소 직후 재시도, 시작 중인 서비스의 실제 수명 잠금, 점유/불확실 lease 보존, 원본 rollback 정리 재시도를 포함한다.

macOS 앱·DMG 빌드와 Tauri backend 68개 테스트(1개 ignored)를 통과했다. 최종 0.9.3 daemon을 격리 실행해 실제 `prepareUninstall` 승인, 잘못된 permit의 `UNINSTALL_PERMIT_MISMATCH`, 올바른 permit의 `cancelUninstall` 성공을 확인했다. 실행 전후 설치된 사용자 native 세션의 PID·supervisor·spawn attempt·상태가 같았다.

Windows 실제 NSIS 빌드와 Tauri backend 63개 테스트(1개 ignored)도 통과했다. 실제 저장소 hooks를 포함한 NSIS 격리 설치기를 실행해, 구 0.9.2가 남긴 무기록 daemon에서 `prepare: UPDATE_RECOVERY_REQUIRED` → `recover: OK` → `prepare: OK` → `finish: OK`를 관측했다. 새 실행 파일 쌍, 실제 DB 배정 재개, 영수증·백업 정리를 확인했으며 기존 자동 실행 등록·격리 환경 밖 서비스는 변하지 않았다.

Windows 소스 검증용 전송에는 처음 Mac tar의 AppleDouble `._` metadata와 bundle manifest가 요구하는 `THIRD_PARTY_NOTICES.md` 누락이 있었다. 두 빌드 실패 출력을 보존했으며, 격리 전송물에서 magic을 확인한 자체 metadata만 정리하고 manifest에 명시된 원본 리소스를 전달했다. 제품 코드나 bundle 검사·라이선스 포함 정책을 완화하지 않았다.

### Windows 사용자 설치본

- 일반 권한 실제 기존 0.9.2 → 동일 서명 setup의 0.9.3 설치: 종료값 0, launcher/service `0.9.3`, `setup --check`의 `ready: true`, 계정 9개와 배정 관련 설정 fingerprint 불변, 복구 영수증·백업 잔여 없음.
- 동일 0.9.3 실제 uninstaller → 파일·서비스 등록 제거/DB 보존 확인 → 동일 서명 setup으로 재설치: 각 종료값 0, 서비스 `0.9.3`, `ready: true`, 계정 9개 fingerprint 불변. `setup --with-omp`는 실행하지 않았다. 제거 전부터 켜져 있던 broker/bridge/observer만 기존 안전 연결 명령으로 복원하고 상태가 같음을 읽어 확인했다. 새 공급자·계정·역할 선택은 켜지 않았다.
- 첫 재설치 harness는 PowerShell의 예약된 `$HOME`과 충돌해 시작 전에 실패했고 증명 파일 대기는 `finite_proof_timeout`이었다. 당시 실제 `aam.exe 0.9.3`와 DB가 남아 있음을 먼저 확인했다. 제거 성공으로 취급하지 않고 harness 변수만 바꾼 뒤 위 실제 제거·재설치 결과를 관측했다.
- 실행한 실제 GUI의 설정 화면에서 `버전 0.9.3`을 읽고 픽셀도 확인했다. 진단 이미지는 계정 식별자가 없는 설정 패널만 보존했다.
- 실제 관리 Claude CLI·Codex CLI, omp의 Ojak Claude bridge·Codex `gpt-6-astra` bridge·직접 `openai-codex/gpt-6-astra` broker까지 총 5개 소비 경로에서 작은 실모델 응답을 확인했다. 각각 종료값 0, 예상 응답 확인, 오류 코드 없음. own native 세션 2개는 preflight 검증 후 `EXITED`, 전후 non-terminal native 0, takeovers 0, 기존 계정 활성화 상태와 연결 구성 불변이었다.
- 소비 경로 harness의 첫 SSH 실행도 5개 모델 호출을 수행했으나 마지막 proof 쓰기에서 parameter 이름 충돌로 실패했다. 원본 실패를 성공 증명으로 재사용하지 않았다. 다음 실행 전 non-terminal 0을 확인했고, 정상 task 실행의 proof와 별도로 기록했다. 두 번 실행의 own native 세션 총 4개는 모두 terminal, 다른 CLI 프로세스 7개는 건드리지 않았다.

### Mac 사용자 선택과 공개 게이트

- 동일 서명 archive를 추출한 앱의 `codesign --verify --deep --strict`와 `aam --version`을 확인했다. 정확한 서명 후보 daemon을 private AAM_HOME/HOME으로 격리 실행해 `serviceVersion: 0.9.3`, 안전 승인, 잘못된 permit 거절, 올바른 취소, live RPC 재취소 거절, 취소 뒤 두 번째 승인·정상 취소를 확인했다. 임시 daemon·fixture는 정리했다.
- 설치된 Mac은 사용 중인 Claude native PID `81363`/supervisor `81337`를 유지했다. 전후 process/supervisor identity·start time·spawn attempt·`ACTIVE` 상태가 같았고 서비스는 `0.9.2`였다.
- 사용자가 **대화 유지**를 선택했다. 따라서 Mac 앱·서비스를 교체하지 않았으며 **정식 공개는 보류**, 0.9.3은 draft로 유지한다. Mac 사용자 설치 반영과 실제 새 서비스 버전/`setup --check` 검증, 두 OS 공개 후 앱 안 업데이트는 아직 실행하지 않았다. 격리 Mac 실행이나 Windows 설치 완료를 두 OS 공개 배포 완료라고 부르지 않는다.

업데이터 서명 검증은 Apple Developer ID 공증·Windows Authenticode와 다르다. 이 후보는 기존 배포 정책대로 Developer ID/공증 및 Authenticode가 없다.

모든 가능한 Windows 환경을 검증했다는 뜻은 아니다. 연결되지 않은 제보 PC, 복수 모니터의 혼합 DPI·디스플레이 hot-plug는 이 복구 검증에서 직접 실행하지 않았다. 이전 CLI/omp·앱 재시작·트레이 검증의 범위는 [0.9.2 기록](0.9.2-verification.md)에 별도로 남아 있다.
